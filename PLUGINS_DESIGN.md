# Плагины Som и плагин Claude: дизайн

Статус (2026-11-12): **сторона `somsrv` реализована** — протокол §5 (`srp_client::plugin`, варианты
`SrvRequest`/`SrvResponse`), движок и Lua API §6 (`crates/somsrv/src/plugin/`), с тестами. Сторона Som
(`PluginView`, загрузка `~/.config/som/plugins`, ответы на `som.*`) и плагин Claude — не начаты.

Механизма плагинов в Som пока нет. Этот документ проектирует его с нуля, а Claude Code — первый плагин,
на котором механизм проверяется.

## 1. Идея

Плагин Som — это **Lua-код, который выполняется в `somsrv` на той машине, где открыта вкладка** (удалённый
хост по ssh, wsl или локальная машина). Плагин запускает процессы, читает их вывод и описывает, что
показать. Som рисует это одной **общей нативной панелью** — Som не знает, что за плагин в ней работает.

Плагин Claude — это `claude.lua`: он запускает `claude` в режиме stream-json, превращает его события в
блоки панели (markdown, диффы, карточки инструментов, кнопки разрешений) и отвечает `claude` на действия
пользователя.

Что это даёт:
- **В Som нет ни строчки про Claude.** Правило «No AI» из `AGENTS.md` не нарушается: Som показывает
  панель плагина, а ИИ — внешний процесс на хосте, которым управляет внешний скрипт.
- **Протокол Claude меняется — правим `claude.lua`**, а не Rust-код Som и `somsrv`.
- **Всё живёт на хосте.** Обрыв ssh не убивает ни `claude`, ни плагин: они принадлежат `somsrv`.
- Панель плагина — та же основа, что нужна для md://-браузера (`SRP_LUA.md`): страница, которую строит
  Lua-бэкенд в `somsrv`.

### Не цели

- Lua на стороне Som (клиентский рендер) — не нужен: плагин описывает **что** показать, Som решает
  **как** нарисовать, в своих цветах и шрифтах. Так все плагины выглядят одинаково.
- Произвольный GPUI из плагинов: только фиксированный набор блоков (§4).
- Магазин плагинов, установка и обновление по сети: плагин — это папка, которую кладут руками.

## 2. Что уже есть

- `somsrv` линкует `mlua 0.10` (`lua54`, `vendored`, `send`). `crates/somsrv/src/lua.rs` — фаза 1 из
  `SRP_LUA.md`: свежий VM на вызов, только `TABLE|STRING|MATH|UTF8|COROUTINE`, никаких Rust-функций,
  скрипт возвращает строку markdown (`SrvRequest::RunLuaScript`). Для плагинов этого мало: нужен
  **постоянный VM с событиями и API**, но песочница-по-белому-списку сохраняется.
- Транспорт к удалённому `somsrv` — link внутри pty-потока вкладки (`crates/somsrv/src/link`), без
  портов и туннелей. Локально — `\\.\pipe\somsrv` / unix-сокет.
- `somsrv` встроен в `som.exe` и сам заливается на удалённые хосты, так что на хосте для плагинов
  ничего ставить не нужно: исходники плагина Som передаёт `somsrv` по проводу (§3).
- `crates/markdown` — GPUI-рендер markdown.
- Поля ввода текста в Som нет (редактор Zed удалён, `EntityInputHandler` вне `gpui` никто не реализует).

## 3. Архитектура

```
 Som (клиент)                               хост вкладки
┌────────────────────────┐                ┌──────────────────────────────────────┐
│ PluginView (Item)      │                │ somsrv                               │
│  блоки: markdown, diff,│   SrvLink      │  └ PluginHost                        │
│  группы, кнопки, ввод  │◄──────────────►│     ├ экземпляр «claude» #1          │
│                        │  view-ops ↓    │     │   Lua VM (постоянный) + поток  │
│ ~/.config/som/plugins/ │  actions  ↑    │     │   claude.lua ⇄ proc: claude -p │
│ (читаются с диска)     │  source   ↓    │     └ экземпляр …                    │
└────────────────────────┘                └──────────────────────────────────────┘
```

- **Экземпляр плагина** = один Lua VM + один поток в `somsrv` + модель вида (дерево блоков). Живёт,
  пока его явно не остановят или пока не умрёт демон. Закрытие вкладки его не останавливает.
- **Плагины лежат на клиенте в `~/.config/som/plugins/<имя>/`** (`plugin.json` + `*.lua`) — так же,
  как темы в `~/.config/som/themes/`. В коде — `paths::plugins_dir()` рядом с `paths::themes_dir()`.
- **Папка отслеживается так же, как `themes/`** (`fs.watch` в `main.rs`): добавил или поправил плагин —
  список в меню обновился сразу. Файлы плагина читаются заново при старте каждого экземпляра: поправил
  `.lua` — перезапусти панель плагина, Som перезапускать не нужно.
- **Исходники плагина едут по проводу.** Som передаёт `somsrv` текст всех `.lua` при старте экземпляра;
  `somsrv` ничего не пишет на диск, на удалённом хосте плагины не хранятся.
- **Версия.** Плагин объявляет в `plugin.json` минимальную версию протокола модели вида (`api`); Som
  с более старым протоколом отказывается его запускать с понятной ошибкой, а не рисует мусор.
- **Плагины в репозитории.** Исходники плагинов, которые делаем мы, лежат в `som/plugins/<имя>/`;
  установка — копирование папки в `~/.config/som/plugins/` (на новой машине — вручную или через
  навык релиза; Som сам ничего не устанавливает и не скачивает).
- **Модель вида хранится в `somsrv`**, а не в Som. При переподключении Som получает снимок модели
  целиком — без журнала событий и без кольцевого буфера.

## 4. Модель вида (общая для всех плагинов)

Панель — вертикальный список блоков + шапка + поле ввода. Блок — `{ id, kind, props, children? }`.

| kind | props | Как рисует Som |
|---|---|---|
| `markdown` | `text` | `crates/markdown` |
| `text` | `text`, `style` (`normal`/`muted`/`error`) | моноширинный текст |
| `code` | `text`, `lang?` | блок кода |
| `diff` | `path`, `old`, `new` | построчный дифф |
| `group` | `title`, `collapsed`, `badge?` | сворачиваемая группа, внутри `children` |
| `actions` | `buttons: [{ id, label, style }]` | ряд кнопок |
| `kv` | `rows: [[k, v]]` | таблица ключ–значение |
| `progress` | `label`, `value?` | спиннер или полоса |

Шапка: `title`, `subtitle`, `status` (`idle`/`busy`/`waiting`/`error` — он же значок на ярлыке вкладки).
Поле ввода: `enabled`, `placeholder`, `multiline`.

Операции `somsrv → Som`: `Snapshot(model)`, `Append{parent?, block}`, `Update{id, props}`,
`Remove{id}`, `Clear`, `Header{…}`, `Input{…}`, `ScrollTo{id}`, `Batch(Vec<ViewOp>)` (§6.2).
Операции `Som → somsrv`: `Action{block_id, button_id}`, `Submit{text}`, `Interrupt`, `Toggle{id}`
(сворачивание запоминается в модели, чтобы пережить переподключение).

Набор блоков растёт по мере надобности, каждый новый kind документируется здесь. Неизвестный Som'у
kind рисуется как `text` с пометкой — старый Som с новым плагином не падает.

## 5. Протокол Som ↔ somsrv

Новые варианты `SrvRequest`/`SrvResponse` (`somsrv::protocol`, копия в `srp_client::protocol`):

```rust
// Som → somsrv
PluginStart { instance: String, manifest: serde_json::Value, sources: Vec<(String, String)>,
              cwd: String, config: serde_json::Value, state: Option<serde_json::Value> }
PluginAttach { instance: String }                  // → PluginView(Snapshot) и дальше поток операций
PluginEvent { instance: String, event: ViewEvent } // Action / Submit / Interrupt / Toggle / Command
PluginSomReply { instance: String, request: u64, reply: SomReply } // Ok(Value) | Err(String)
PluginStop { instance: String }
ListPlugins

// somsrv → Som
PluginView { instance: String, op: ViewOp }
PluginSomRequest { instance: String, request: u64, call: SomCall } // som.* (§6.9)
PluginState { instance: String, state: serde_json::Value }         // state.save (§6.8) → db.json
PluginExited { instance: String, error: Option<String> }
Plugins(Vec<PluginInfo>)                          // instance, plugin, version, cwd, title, status
```

- `SomCall` — `OpenTerminal`/`Notify`/`Preview`/`ClipboardWrite`/`Confirm`/`OpenUrl`/`OpenPlugin`.
  Som проверяет разрешение по манифесту **сам** (не доверяет `somsrv`) и отвечает `PluginSomReply`
  с результатом или ошибкой (`denied`, `unsupported`). Если Som не подключён, `somsrv` сразу отвечает
  плагину `detached`, ничего не отправляя.

- `instance` выдаёт Som (UUID строкой, как у tmux-сессий). Имя и версия плагина — из `manifest`.
- `sources` — все `.lua` плагина (имя модуля → текст); `require` внутри VM ищет только в них.
- `config` — секция плагина из `settings.json` Som (§8).
- `state` — последнее `PluginState` этого экземпляра из `db.json` (при перезапуске после гибели демона).

## 6. Lua API плагина

Весь API — функции Lua-движка в `somsrv`. Он делится на две части:

- **Выполняется в `somsrv`:** события, модель панели, процессы, таймеры, данные, состояние, лог. Всё это
  работает и тогда, когда Som отключён (обрыв ssh, закрытая вкладка).
- **Пересылается в Som (`som.*`):** просьбы к клиенту. Если Som не подключён, вызов возвращает ошибку
  `detached`, и плагин сам решает, что делать (например, отложить уведомление до `attach`).

Пометки: **0** — ядро движка (этап 0), **C** — нужно плагину Claude, **П** — позже, по требованию первого
плагина, которому это понадобится. Пункты П перечислены заранее, чтобы потом не ломать API.

### 6.1. События: `plugin.on(event, fn)`

| Событие | Когда | |
|---|---|---|
| `start(ctx)` | запуск экземпляра; `ctx.cwd` (cwd вкладки), `ctx.config` (§8), `ctx.state` (§6.8) | 0 |
| `stop()` | остановка экземпляра | 0 |
| `attach()` / `detach()` | Som подключился / отключился | 0 |
| `submit(text)` | отправлен текст из поля ввода | 0 |
| `action(block_id, button_id)` | нажата кнопка в блоке | 0 |
| `interrupt()` | Esc / «Стоп» | 0 |
| `command(name)` | клавиша или пункт меню из `commands` манифеста | П |
| `complete(prefix)` → список | подсказки в поле ввода (`@файлы`) | П |

`attach`/`detach` нужны, чтобы плагин знал, смотрит ли кто-то на панель: например, Claude закончил ход
при закрытой панели — плагин запоминает это и уведомляет при подключении.

### 6.2. Модель панели: `ui.*`

Модель хранится в `somsrv`. Если Som подключён, изменения уходят ему сразу; при подключении Som получает
снимок целиком (§3).

| Функция | |
|---|---|
| `ui.header{title, subtitle, status}` | 0 |
| `ui.append{kind, props, parent?}` → id | 0 |
| `ui.update(id, props)`, `ui.remove(id)`, `ui.clear()` | 0 |
| `ui.input{enabled, placeholder, multiline}` | 0 |
| `ui.batch(fn)` — все операции внутри `fn` уходят одним пакетом (стриминг ответа) | 0 |
| `ui.scroll_to(id)` | C |

### 6.3. Процессы: `proc.*`

Только программы из `spawn` манифеста (§7).

| Функция | |
|---|---|
| `proc.spawn{program, args, cwd, env, mode = "lines" \| "bytes"}` → `p` | 0 |
| `p:write(data)`, `p:close_stdin()`, `p:kill()`, `p.pid` | 0 |
| события `line(p, s)` (`mode = "lines"`), `stdout(p, bytes)` (`mode = "bytes"`), `stderr(p, chunk)`, `exit(p, code)` | 0 |

PTY в API нет: если нужен терминал, плагин просит Som открыть вкладку (`som.open_terminal`).

### 6.4. Время

`timer.after(ms, name)`, `timer.every(ms, name)`, `timer.cancel(name)`, событие `timer(name)`;
`time.now()` — **0**.

### 6.5. Данные

`json.encode(t)` / `json.decode(s)` — **0**. Строки, таблицы и `utf8` — из stdlib.

### 6.6. Хост

`host.os()`, `host.name()`, `host.home()`, `host.env(name)` — **0**. cwd вкладки — в `ctx.cwd`.

### 6.7. Лог

`log.info(...)`, `log.warn(...)`, `log.error(...)` — **0**. Пишет в лог `somsrv`; последние строки
видны в Som в отладочном блоке панели.

### 6.8. Состояние

`state.save(t)` — **C**. Таблица (JSON-совместимая) хранится в памяти `somsrv` и копируется в `db.json` на
клиенте рядом с записью о панели. После перезапуска демона Som стартует экземпляр заново и передаёт её в
`ctx.state`. Пример: `claude.lua` сохраняет `sid` для `--resume`. На диск хоста ничего не пишется.

### 6.9. Запросы к Som: `som.*`

| Функция | | Разрешение (§7) |
|---|---|---|
| `som.api`, `som.has(name)` — версия API и проверка функции | 0 | — |
| `som.open_terminal{cmd, cwd}` — терминальная вкладка на том же хосте | C | `terminal` |
| `som.notify{title, body}` — сообщение в Som, вне фокуса — уведомление ОС | C | `notify` |
| `som.preview(path)` — показать файл хоста через SRP | C | `preview` |
| `som.clipboard_write(text)` — буфер обмена клиента | C | `clipboard` |
| `som.confirm{text, buttons}` → выбор — модальный вопрос | П | — |
| `som.open_url(url)` — ссылка в браузере клиента | П | `open_url` |
| `som.open_plugin{name, config}` — открыть панель другого плагина | П | — |

Чтения буфера обмена нет сознательно: удалённому плагину незачем видеть буфер клиента.

### 6.10. Правила движка

- **Один поток и одна очередь событий на экземпляр.** Каждый обработчик выполняется как корутина;
  функции, ждущие ответа (`som.confirm`), приостанавливают обработчик, а не поток — остальные события
  тем временем обрабатываются.
- **Лимит на обработчик** — по счётчику инструкций (`mlua` hook). Зациклившийся плагин получает ошибку
  в шапку панели; `somsrv` и другие экземпляры работают дальше. Ошибка или паника Lua не роняет демон.
- **Песочница:** stdlib — `TABLE|STRING|MATH|UTF8|COROUTINE`, без `io`, `os`, `package`; `require`
  ищет модули только среди файлов плагина.
- **Инструменты для запущенных процессов** (`mcp.tool`) и вызовы `term_*`/`som_test_*`/`desk_*` для
  живых тестов — §15.
- **Позже, отдельными разрешениями:** `fs.read`/`fs.list` с корнями из манифеста, `http.get` поверх
  существующего `http_fetch.rs`. Файлы и сеть через stdlib не открываем.

## 7. Манифест и песочница

`~/.config/som/plugins/claude/plugin.json`:

```json
{
  "name": "claude",
  "version": "1",
  "api": 1,
  "title": "Claude Code",
  "entry": "main.lua",
  "spawn": ["claude"],
  "permissions": ["terminal", "notify", "preview", "clipboard"],
  "launch": { "label": "Claude здесь", "keys": "ctrl-shift-c" },
  "commands": []
}
```

- `spawn` — белый список программ для `proc.spawn`; пустой — плагин процессов не запускает.
- `permissions` — какие `som.*` плагину разрешены (§6.9). Som проверяет их сам при каждом запросе.
- Файловой системы и сети у плагина нет (нет `io`, `os`, `package`), пока не появится плагин, которому
  это нужно, — тогда добавляется отдельная разрешаемая функция, а не stdlib целиком (как в `SRP_LUA.md`).
- `launch` — пункт, который Som добавляет в палитру/меню терминальной вкладки для запуска плагина.
- `commands` — `[{ name, label, keys }]`: действия внутри открытой панели, приходят событием
  `command(name)` (§6.1, этап П).

## 9. Плагин Claude (`som/plugins/claude/` → `~/.config/som/plugins/claude/`)

**Старт** (`start`): `proc.spawn` `claude -p --input-format stream-json --output-format stream-json
--verbose --permission-prompt-tool stdio [--resume <sid>] [--model …]` в cwd вкладки (OSC 7, иначе
домашний каталог); шапка — `busy`.

**Разбор stdout** (`line` → `json.decode`):

| Событие claude | Блоки |
|---|---|
| `system`/`init` | шапка: модель, cwd; `sid` сохраняется через `state.save` |
| `assistant` → `text` | `markdown` (дописывается `update`, если ход стримится) |
| `assistant` → `thinking` | свёрнутая `group` «Размышления» с `markdown` внутри |
| `assistant` → `tool_use` | `group` с названием инструмента: `Bash` → `code`; `Edit`/`MultiEdit` → `diff`; `Write` → `code`; `Read`/`Grep`/`Glob` → одна строка; прочее → `code` с JSON |
| `user` → `tool_result` | внутрь той же группы, свёрнуто, длинное обрезано |
| `control_request`/`can_use_tool` | `actions`: «Разрешить», «Разрешить всегда», «Отклонить»; шапка — `waiting` |
| `result` | `kv` с длительностью, токенами, стоимостью; шапка — `idle` |
| неизвестное | `code` с сырой строкой |

**Ввод:** `submit` → `{"type":"user","message":…}` в stdin. `action` по кнопке разрешения →
`control_response`, блок с кнопками заменяется строкой с решением. `interrupt` → control-запрос
`interrupt`.

**Переход в TUI:** кнопка в шапке → `p:kill()` и `som.open_terminal{ cmd = { "claude", "--resume", sid } }`.

**Конец хода при закрытой панели** (`detach` был, `attach` не было): `som.notify` вернёт `detached`,
плагин запоминает флаг и при `attach` показывает уведомление «Claude закончил».

**Пути в выводе** инструментов: кнопка «Показать» → `som.preview(path)` для картинок и markdown.

**Перезапуск демона** (новая сборка `somsrv` убивает старый — так задумано): экземпляры плагинов
гибнут вместе с ним. Som при следующем подключении видит, что `instance` исчез, и стартует плагин
заново с тем же `sid` в `config` → `claude --resume`. История восстанавливается из
`~/.claude/projects` хоста, незаконченный ход теряется — плагин пишет об этом блоком `text`/`error`.

Control-часть stream-json документирована не полностью: формат `can_use_tool`/`interrupt` берём из
исходников Agent SDK и проверяем на этапе 1. При расхождении правится только `claude.lua`.

## 10. Som: `PluginView`

- Новый крейт `plugin_view` (`terminal_view` трогать нельзя по `AGENTS.md`): `Item` воркспейса,
  виртуализированный `gpui::list` блоков, шапка, поле ввода.
- Цвета, шрифты, отступы — только из темы Som.
- Пути в блоках кликабельны: открыть на том же хосте в новой терминальной вкладке.
- Поле ввода — своё, на `EntityInputHandler` (IME, русская раскладка, история, Shift+Enter). Пока его
  нет — однострочная строка.
- На клиенте ничего не пишется на диск: модель — в `somsrv`, список открытых панелей — в `db.json`
  (как вкладки).

## 11. Тесты

- `PluginHost` (без Som): Lua-плагин + фейковый процесс, печатающий записанный поток → ожидаемая модель
  вида; лимит времени обработчика; ошибка Lua не роняет хост; песочница (`io`, `os`, `require` вне
  `sources`, `proc.spawn` не из белого списка — всё отказ).
- `claude.lua`: реальные потоки stream-json, снятые на этапе 1, — регрессионные тесты плагина на том же
  стенде. Новая версия `claude` = новый записанный поток.
- `PluginView`: GPUI headless-тесты на снимках модели.
- Тесты с реальным демоном — только с `SOMSRV_KEEP_DAEMON=1`.

## 14. Риски

- **Объём механизма плагинов** больше, чем у одной Claude-панели: `PluginHost`, протокол модели вида,
  общий виджет. Окупается вторым плагином; если второго не будет — это переплата.
- **Выразительность блоков.** Если плагину понадобится то, чего нет в §4, придётся расширять Som.
  Смягчение: неизвестные kind деградируют до текста; набор растёт по требованию.
- **Дрейф протокола `claude`** — теперь правится в Lua, но всё равно правится. Записанные потоки
  ловят это в тестах.
- **Поле ввода** — самая дорогая часть UI, отложена на этап 3.
- **Производительность**: частые `update` при стриминге ответа. Som сливает операции до кадра, `somsrv`
  может склеивать подряд идущие `update` одного блока.

## 15. Живые тесты и управление программами

Claude в плагине работает на хосте вкладки, а окна, которые надо проверять, — на клиенте (или в
терминале на хосте). Инструментов Claude Desktop (скриншоты, клики) у него там нет. Их даёт Som:
плагин передаёт `claude` набор MCP-инструментов, а выполняет их Som на клиенте. Тестировать можно
что угодно, не только Som. Три уровня, от самого точного к самому общему; Claude берёт самый точный,
который подходит.

### 15.1. Как инструменты доходят до Claude

```
claude (хост) ──stdio MCP──► somsrv mcp --instance <id> ──► демон ──► экземпляр плагина (Lua)
                                                                         │ som.* (§15.3–15.5)
Som (клиент) ◄──────────────────── link внутри pty ◄─────────────────────┘
```

- **`mcp.tool{ name, description, schema, handler }`** — новая функция Lua API (общая, не про Claude):
  плагин объявляет инструменты, `handler(args)` выполняется как обычный обработчик-корутина и может
  ждать `som.*`. Возвращённая таблица — результат инструмента; картинка — `{ image = <png bytes> }`.
- **`somsrv mcp --instance <id>`** — подкоманда того же бинарника: stdio MCP-сервер, который подключается
  к демону и передаёт `tools/list` и `tools/call` экземпляру (новые сообщения `PluginToolList` /
  `PluginToolCall` / `PluginToolResult`). На хосте ничего не ставится.
- `claude.lua` запускает `claude` с `--mcp-config`, где сервер `som` — эта подкоманда; `somsrv`
  в `spawn` манифеста не нужен: его запускает `claude`, а не плагин.

### 15.2. Уровень 1 — терминальные программы (на клиенте и на хосте)

micro, farsh, yazi, edit, любые TUI и CLI. Som открывает **тестовую вкладку** — локальную или на любом
хосте по ssh/wsl — и даёт Claude её сетку, а не пиксели:

| Инструмент | |
|---|---|
| `term_open{ profile?, cmd?, cwd?, cols?, rows? }` → tab | тестовая вкладка (в отдельном окне, не среди вкладок пользователя) |
| `term_type(tab, text)`, `term_keys(tab, keys)` | ввод (`"ctrl-o"`, `"f3"`, `"esc"`) |
| `term_read(tab)` | текст сетки, позиция и вид курсора, размеры; цвета — по запросу |
| `term_wait_for(tab, text \| regex, timeout)` | ожидание вместо `sleep` |
| `term_placements(tab)` | SRP-размещения (картинки, видео, markdown) и их состояние |
| `term_close(tab)` | |

Фокус, окна и координаты не участвуют; проверка точная до символа. Разрешение — `terminal_control`.

### 15.3. Уровень 2 — сам Som

| Инструмент | |
|---|---|
| `som_test_start{ build? }` / `som_test_stop` | **отдельный тестовый Som**: свой config-каталог, `SOMSRV_KEEP_DAEMON=1`, без `NO_COLOR` из окружения; Som пользователя и его демон не трогаются |
| `som_test_keys`, `som_test_read(tab)`, `som_test_screenshot(region?)`, `som_test_burst(n, ms)` | ввод внутрь его GPUI, чтение его модели, кадры (серия — для мимолётных багов, как навык `som-window-capture`) |

Тестовый Som управляется по своему каналу, а не через ОС: ни AutoIt, ни `SetForegroundWindow`.
Разрешение — `som_control`.

### 15.4. Уровень 3 — любая программа на рабочем столе клиента

TrafficMonitor, клиент WoW, браузер — что угодно. Som сам делает то, что делает computer-use Claude
Desktop, нативно:

| Инструмент | Windows | Зачем так |
|---|---|---|
| `desk_apps`, `desk_windows` | список процессов и окон | |
| `desk_screenshot(window)` | `PrintWindow` окна | окно может быть перекрыто, фокус не нужен |
| `desk_tree(window)` | UI Automation: элементы, текст, состояние | проверять текст, а не пиксели |
| `desk_invoke(element)`, `desk_set_value(element, text)` | шаблоны UIA Invoke / Value | нажатие без мыши и фокуса |
| `desk_click(window, x, y)`, `desk_keys`, `desk_type` | `SendInput` | запасной путь |

`SendInput` уходит окну с фокусом, поэтому Som **проверяет окно переднего плана прямо перед каждой
инъекцией** и при несовпадении останавливается с ошибкой, а не вводит наугад (урок AutoIt и
TrafficMonitor, который забирает фокус). macOS: `CGWindowListCreateImage`, Accessibility API, `CGEvent`.
Linux (AT-SPI, X11/portal) — позже. Разрешение — `desktop_control`.

### 15.5. Безопасность уровня 3

Процесс на удалённом хосте управляет рабочим столом пользователя, поэтому:

- **Разрешение даёт только клиент.** Первое обращение к приложению показывает в Som карточку «Claude
  хочет управлять TrafficMonitor.exe»; разрешение — на одно приложение и один экземпляр плагина, до его
  остановки. Ни плагин, ни `somsrv` не могут выдать его сами; `desktop_control` в манифесте лишь
  разрешает спросить.
- **Уровни по типу приложения:** браузеры и менеджеры паролей — только чтение (скриншот, дерево);
  терминалы и IDE — только клики; остальное — полный доступ.
- **Управление видно:** рамка вокруг управляемого окна и значок на вкладке плагина. Горячая клавиша
  (`ctrl-alt-escape`) мгновенно отзывает все разрешения всех экземпляров.
- Ввод в поля паролей (UIA `IsPassword`) запрещён всегда.
- Правило «предупредить перед живым тестом и дождаться ок» выполняется самим механизмом: на уровнях 2 и
  3 первое управление невозможно без «Разрешить» в карточке.

### 15.6. Порядок

Уровень 1 — первым (дёшево и покрывает большинство тестов), уровень 2 — следом, уровень 3 — отдельным
этапом с упором на §15.5 (§12, этапы 5–7).

## 16. Работа через SSH: что проверено по коду и что нужно сделать

Проверено 2026-11-12.

### 16.1. Что уже есть

- Вкладка профиля с `tmux`, `srp` или `lua` (`terminal_panel::wants_srp`) запускает на хосте relay
  `/tmp/som-somsrv/somsrv`, и в её pty-потоке живёт канал к демону хоста (`Terminal::srv_link`,
  `somsrv::link`). Сообщения `Plugin*` идут по нему без доработки: канал их не разбирает.
- `somsrv` доставляется на хост перед открытием вкладки (`ensure_remote_binary_deployed`).
- Движок плагинов (§6) одинаков на Windows и на хосте.

### 16.2. Проблемы и решения

1. **Демон хоста не найдёт `claude`.** Relay запускается как `ssh -tt host /tmp/som-somsrv/somsrv …` —
   не login-сеанс; `-l` получает только шелл вкладки. Демон наследует урезанный `PATH` relay, а
   `~/.local/bin` (куда ставится `claude`) на Debian добавляет только `~/.profile`.
   → `somsrv` на Unix ищет программу из `spawn` через `$SHELL -lc 'command -v <имя>'` (один раз на
   экземпляр, с учётом мусора в выводе login-шелла). В манифесте остаётся `"claude"`.
2. **Som не знает cwd удалённой вкладки** (`Terminal::working_directory()` для удалённых — `None`).
   → `PluginStart` несёт `pane_id` вкладки; шелл вкладки держит демон хоста (`session.rs` знает его
   `pid`), и демон берёт cwd шелла через `sysinfo`. Без OSC 7 и без интеграции с шеллом.
3. **Канал живёт, пока жива вкладка** (`srv_link` принадлежит терминалу).
   → Этап 0–1: панель привязана к вкладке, из которой открыта; после её закрытия панель
   подключается через любую другую вкладку на тот же хост. Экземпляр на хосте при этом живёт.
   → Позже: собственный канал панели — `somsrv --link` (без шелла) поверх `ssh host …` на обычных
   пайпах, один на хост, с переподключением и `PluginAttach` → снимок.
4. **Обновление Som прерывает Claude на хосте.** Новый `somsrv` заменяет демон хоста (так задумано), и
   все экземпляры гибнут.
   → Плагин восстанавливается через `state.save` + `--resume` (теряется только текущий ход).
   → Перед заменой демона Som спрашивает у него `ListPlugins`; если идёт работа — спрашивает
   пользователя: «На deb работает Claude, обновление прервёт ход — обновить сейчас / позже?».
   → Отдельный держатель процессов, переживающий смену демона, не делаем: это «демон не той версии».
5. **Claude на хосте должен быть залогинен.** Ошибку авторизации в `result` `claude.lua` показывает
   кнопкой «Войти» → `som.open_terminal{ cmd = { "claude", "/login" } }`. Токены остаются на хосте.

Мелочи: большие `tool_result` Lua хранит целиком у себя, в панель идёт обрезанный текст и кнопка
«Показать всё»; второй Som, подключившийся к тому же экземпляру, забирает панель (уже так);
ssh на Windows-хост — вне рамок.

### 16.3. Порядок

1. Som, этап 0: `paths::plugins_dir()`, загрузка плагинов, клиент `Plugin*` поверх канала вкладки,
   `PluginView` (`markdown`/`text`/`code`, однострочный ввод), действие «Плагин здесь» во вкладке;
   проверка на deb плагином `echo`.
2. `somsrv`: поиск программ через login-шелл (п. 1), cwd по `pane_id` (п. 2).
3. `claude.lua`, этап 1: разговор, `--resume`, «Войти».
4. Предупреждение перед заменой демона с работающими плагинами (п. 4).
5. Собственный канал панели, `somsrv --link` (п. 3).
