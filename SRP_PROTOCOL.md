# Som Rich Protocol (SRP)

Собственный бинарный протокол Som для передачи медиа/rich-контента через PTY — независимый от Kitty Graphics Protocol, который остаётся нетронутым для совместимости со сторонними клиентами (yazi и т.п.).

Этот документ фиксирует все значимые архитектурные и технические решения по ходу реализации — не туториал, а рабочий журнал решений с обоснованием "почему", чтобы не терять контекст между сессиями.

## Зачем свой протокол, а не Kitty

Измерено: Kitty-путь (PNG-перекодирование каждого кадра + base64 через APC) для 47-кадрового GIF 256×256 даёт 5.3MB трафика — многосекундные паузы, неприемлемо для анимации, тем более для аудио/видео 4K60 в будущем. Причина — Kitty обязан оставаться 7-бит-safe (base64), потому что таков стандарт, которому он следует ради совместимости со сторонними клиентами.

У SRP нет такого обязательства — свой протокол, свой клиент, свой вьюер. Решено: **полностью отдельная система**, не переиспользующая ни транспорт, ни хранилище (`ImageStore`), ни paint-путь Kitty — они физически делят только один и тот же PTY-канал (разные marker-байты).

## Модель передачи: progressive file copy

Клиент (`somcat --stream <file>`) копирует РЕАЛЬНЫЙ файл побайтово, без перекодирования, chunk-за-chunk, в локальный кэш-файл на машине, где физически работает Som. Плеер начинает декодирование/показ до того, как файл докачан целиком — принципиальное отличие от старого Kitty-animation-пути, где decode ждал полного `a=T`.

Транспорт живёт целиком внутри PTY (никаких новых TCP/UDP портов, никаких сокетов в обход PTY) — работает через существующий SSH-канал (порт 22) без дополнительной инфраструктуры, включая som-tmux relay "бесплатно" (som-tmux уже прозрачно релеит любые APC-байты — см. `kitty_replay.rs`).

## VTE-патч: полный 8-бит APC

**Файл:** `errordnk/vte` (форк, локальный клон `C:\home\dnk\vte-fork-work`), коммит `649d0a6`. `errordnk/alacritty` обновлён на новый vte-rev, коммит `c9f86ad4`. `som`'s `Cargo.toml:151` — `rev = "c9f86ad4"`.

Оригинальный (непатченый) `advance_apc_string` пропускал только `0x00-0x17,0x19,0x1C-0x7E` (7-бит ASCII минус `0x18,0x1A,0x1B`) — весь диапазон `0x80-0xFF` молча терялся, `0x9C` (8-bit ST) обрывал строку, `0x7F` (DEL) молча терялся. Это и вынуждало Kitty на base64.

**Патч**: `advance_apc_string` теперь пропускает через `apc_put` ЛЮБОЙ байт кроме `0x1B` (единственный terminator, как и раньше — `ESC \`). `0x18/0x1A` (CAN/SUB — историческая VT100 семантика "оператор прерывает застрявшую escape-последовательность вручную") тоже разрешены как данные — для протокола, где отправитель это программа, а не человек за клавиатурой, этот класс сигналов не нужен. `0x9C` (8-bit ST) убран как терминатор — SRP всегда использует 7-битный `ESC \`.

Риск патча минимален: изменение изолировано в одной маленькой функции, вызываемой только в состоянии `State::ApcString` — весь остальной парсинг (CSI/OSC/Escape/Ground) не затронут. Kitty-протокол тоже не задет: он никогда не эмитит байты из вновь разблокированного диапазона (base64-алфавит — чистый ASCII).

## Формат конверта

```
[marker:            1 byte  = b'S']
[version:           1 byte  = 1]
[content_type:      1 byte  = ContentType as u8]  // 0=Gif, 1=Audio, 2=Markdown, 3=Video (резерв)
[trailing_esc_byte: 1 byte  = 0 or 1]
[session_id:        4 bytes LE]
[file_id:           4 bytes LE]
[chunk_offset:      8 bytes LE]
[chunk_len:         4 bytes LE]
[total_size:        8 bytes LE, 0 = неизвестен]
[crc32:             4 bytes LE, только над payload]
[payload:           chunk_len bytes]
```

Отправляется как `ESC _ S <envelope> ESC \`. Marker `S` отличает от Kitty's `G` — парсеры взаимоисключающи по построению (`kitty_graphics::parse_command` требует `G` и возвращает `None` иначе).

**Файл:** `crates/terminal/src/rich_content_transport.rs`.

## КРИТИЧНО: payload никогда не содержит 0x1B — почему escaping не работает

Первая попытка дизайна: escape `0x1B` → `0x1B 0x1B` внутри payload, unescape при парсинге (как классический byte-stuffing). **Оказалось логически сломанным**: патченый VTE-парсер обрывает APC-строку на ПЕРВОМ `0x1B` любой такой пары БЕЗУСЛОВНО — он не понимает прикладную семантику "это экранированный ESC, продолжай". Патчить VTE ещё раз ради понимания escape-пар — рассмотрено и отклонено (усложнило бы общий парсер деталью одного протокола).

Пойман РЕАЛЬНЫМ end-to-end тестом через настоящий VTE-парсер — изолированные unit-тесты `parse_envelope`/`build_envelope` "проходили" (тестировали только чистые функции), но не через реальный APC-hook/put/unhook путь.

**Решение**: `payload` — жёсткий инвариант, НИКОГДА не содержит `0x1B`. `build_envelope` паникует при нарушении (programmer error, не runtime-состояние). Вместо escaping — поле заголовка `trailing_esc_byte: bool`: если `true`, получатель дописывает ровно один литеральный `0x1B` в файл сразу после payload этого чанка. Клиентская функция `split_into_chunks(data, max_len) -> Vec<(Vec<u8>, bool)>` режет исходные байты на куски, гарантированно свободные от `0x1B`, с корректным флагом на каждом.

Для реального GIF-файла `0x1B` встречается часто (сжатые данные) — 980KB файл дал 3320 чанков вместо ожидаемых ~240 (примерно 1 чанк на 295 байт). Это ожидаемый оверхед данной схемы, не баг.

## КРИТИЧНО: std::io::Stdout::flush() виснет на Windows/ConPTY с бинарными данными

**Симптом**: `somcat --stream` намертво зависал в реальном ConPTY-тесте (headless `#[gpui::test]`), но работал мгновенно при простом файловом pipe-редиректе — разница ставила в тупик несколько итераций диагностики.

**Корень**: `std::io::Stdout` на Windows оборачивает handle в `LineWriter`, который флашит внутренний userspace-буфер только до последнего увиденного `\n` (0x0A). Бинарный SRP-конверт почти никогда не содержит настоящий `\n`. `write_all()` сам по себе возвращал `Ok` (данные просто копились в буфере), но explicit `.flush()` СРАЗУ ПОСЛЕ него блокировался навсегда на первом же чанке (113 байт) — воспроизводилось стабильно 100% раз.

Kitty-путь (`send_chunked`/`print!`) никогда не сталкивался с этим: base64-текст, `println!()` между изображениями — реальные `\n`-байты частые, `LineWriter` флашится сам без явного вызова.

**Решение**: `write_raw_stdout()` — на Windows пишет напрямую через `WriteFile` (Win32 API) на `STD_OUTPUT_HANDLE`, полностью обходя `std::io::Stdout`/`LineWriter`. На Unix обычный `write_all` (там `LineWriter`-проблемы для pipe/pty-таргета нет).

**Файл:** `crates/somcat/src/main.rs`, функция `write_raw_stdout`.

## Клиентский режим: somcat --stream

`somcat --stream <file>` — отдельный от Kitty-пути код в `main()`, не требует `raw_mode::enable()` полностью (нет query/negotiation — SRP не optional-with-fallback внешний стандарт), но требует `raw_mode::enable_output_vt_processing()` (новая функция, устанавливает `ENABLE_VIRTUAL_TERMINAL_PROCESSING` только на output-handle, не трогая stdin — старый `enable()` падал с "handle is invalid" при отсутствии реального stdin TTY).

Content-type определяется по расширению файла (`.gif` → `ContentType::Gif`, остальное пока не реализовано).

## Серверная сторона

- `crates/terminal/src/rich_content_cache.rs` — `RichContentCache`: progressive on-disk writer с watermark-трекингом (`contiguous_len`), поддержка out-of-order чанков через `pending_ranges`. Путь кэша: `paths::config_dir().join("media_cache")` в production, `std::env::temp_dir()` в тестах (`paths::config_dir()` — process-global `OnceLock`, не test-aware).
- `crates/terminal/src/rich_content_gif_player.rs` — `try_decode_progressive`: инкрементальный GIF-декод по мере роста файла. **Важная находка**: `gif` crate's `DecodingError::UnexpectedEof` НЕ оборачивает `std::io::Error` (`source()` возвращает `None`) — приходится матчить по тексту "Unexpected End of File", не по типу ошибки.
- Роутинг в `Terminal::process_event` (`crates/terminal/src/terminal.rs`): проверка `bytes.first() == Some(rich_content_transport::MARKER)` перед Kitty-парсингом.

### НЕ РЕШЕНО — активная проблема на момент паузы

После фикса `flush()`-бага транспорт стал реально доставлять данные: bench-тест `bench_rich_content_stream_progressive_playback_starts_before_transfer_completes` показывает **3320/3320 чанков успешно доходят до `Terminal::process_event` и парсятся без единой ошибки** (`log::trace!`/`eprintln!` diagnostic "DIAG: rich-content bytes.len()=..." сработал 3320 раз, 0 раз "rich-content chunk write failed").

**НО** тест всё равно падает (`first_partial_frame_count == 0`) — GIF ни разу не декодировался даже частично. При этом `terminal.get_content()` (реальный видимый грид терминала) показывает **явно "мусорный" бинарный текст** на части опросов (например: `"\u{a0}▓ЎKbфАуВх\twd6а..."` — похоже на сырые байты GIF-файла, отрендеренные как cp866/OEM-текст).

**Рабочая гипотеза (не подтверждена)**: где-то посреди потока APC-строк VTE-парсер теряет/прерывает `ApcString`-состояние преждевременно (до настоящего `ESC \` конца конверта), и остаток байт ЭТОГО конверта (или следующих) интерпретируется заново с состояния `Ground` — то есть напрямую как видимый текст в гриде, а не как APC payload. Раз `payload` формально гарантированно свободен от `0x1B` (единственного байта, который патченый VTE трактует special), И количество успешных `DIAG: rich-content` совпадает с ожидаемым числом чанков (3320) — открытый вопрос: если ВСЕ конверты долетели до парсера УСПЕШНО (иначе `DIAG` не сработал бы), откуда тогда мусорный текст в гриде? Возможные направления для продолжения:
1. Может быть мусор — это остаток от ОЧень старого теста/сессии, не от текущего прогона (стоит явно создать чистый temp cache dir с уникальным именем на каждый запуск теста и проверить содержимое ИМЕННО оттуда, не полагаться на `get_content()`).
2. Может быть баг НЕ в VTE/APC-путях, а в моей собственной тестовой логике опроса (`still_running` всегда `true` подозрительно — возможно баг в `completion_rx.try_recv()`, использую его дважды в одной итерации, что "съедает" сообщение — см. код теста, TODO почистить эту логику отдельно от основной диагностики).
3. Проверить — может ли часть APC-строк, которые я строю в `stream_file`, случайно НЕ иметь `ESC _` в начале (баг сборки `apc`-вектора), из-за чего они посылаются как голый текст изначально, а не теряют APC-статус в процессе.
4. Следующий конкретный шаг: временно уменьшить объём тестового файла до 2-3 чанков (не всю giphy.gif), включить построчную детальную diagnostic-печать КАЖДОГО отправленного APC-конверта побайтово (hex dump) на стороне клиента, и сравнить с тем, что реально пришло в `parse_envelope` на стороне сервера — побайтовое сравнение отправленного/полученного укажет точную точку расхождения, если она есть.

### Дополнительно найденный, не связанный баг в тестовой логике
`terminal.rs`'s `bench_rich_content_stream_progressive_playback_starts_before_transfer_completes` вызывает `completion_rx.try_recv()` ДВАЖДЫ в одной итерации цикла (один раз в основной логике `still_running`, второй раз в diagnostic-блоке `if i % 20 == 0`) — второй вызов "съедает" уже полученное сообщение о завершении процесса, ошибочно показывая `still_running=true` даже после того как процесс реально завершился. Нужно почистить перед финализацией теста — использовать сохранённое значение, не вызывать `try_recv()` повторно.

### Уточнение по "мусору на экране" (проверено дальше, ещё не разрешено)
Подтверждено: `screen="..."` в diagnostic-выводе — это РЕАЛЬНОЕ содержимое `term.get_content()` (читает настоящий grid терминала через `alacritty_terminal`), не путаница с соседними eprintln-строками в общем логе. Значит бинарные байты РЕАЛЬНО оказываются в видимом гриде как текст.

Проверено и ИСКЛЮЧЕНО:
- Коллизия file_id между запусками теста через общую `%TEMP%\som_rich_content_cache_runtime\` директорию — файлы именуются `{session:08x}-{file:08x}.ext`, разных запусков разные `now_ms` → разные имена, коллизий не найдено (проверено содержимое директории напрямую).
- Диагностические `eprintln!` в клиенте (`somcat`) — все убраны, подтверждено `grep`.
- `eprintln!("DIAG: rich-content bytes.len()...")` на строке 1277 `terminal.rs` — это ДРУГОЙ, безобидный debug-вывод внутри `process_event` (сработавший ровно 3320 раз, что совпадает с числом реально отправленных чанков) — не источник мусора в гриде, просто рядом в том же логе.

**Ключевой нерешённый парадокс**: количество успешных "DIAG: rich-content bytes.len()" срабатываний (3320) ТОЧНО совпадает с количеством чанков, которые клиент должен был отправить (`split_into_chunks` на 980658-байтовый файл с `CHUNK_SIZE=4096` дал 3320 pieces, подтверждено логом клиента "3320 pieces to send"). Если КАЖДЫЙ чанк успешно дошёл до `parse_envelope`/`process_event` (что означает — обёртка `ESC _ ... ESC \` была корректно распознана как APC каждый раз, иначе `parse_envelope` даже не вызвался бы, так как байты пошли бы в Ground-состояние вместо ApcString) — тогда ОТКУДА берётся мусорный текст в гриде? Гипотеза на продолжение: возможно, мусор — это не байты SRP-протокола вообще, а что-то ДРУГОЕ, отправленное ДО или ПОСЛЕ потока чанков (например, само `giphy.gif`-имя файла в usage-сообщении об ошибке, или содержимое STDIN echo от pwsh/shell-обвязки, если тест использует `build_test_terminal_with_arguments` с промежуточным shell). Нужно проверить точное содержимое argv/program переданное в тест — не заворачивается ли `somcat.exe --stream <path>` через что-то, что ДОПОЛНИТЕЛЬНО печатает путь как текст (echo команды) прежде чем сам somcat стартует.
