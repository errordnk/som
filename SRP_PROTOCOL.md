# Som Rich Protocol (SRP)

Собственный бинарный протокол Som для передачи медиа/rich-контента через PTY. Раньше сосуществовал с реализацией Kitty Graphics Protocol; Kitty был полностью вырезан из кодовой базы (см. секцию "Kitty Graphics Protocol вырезан" ниже) — SRP теперь единственный способ показать изображение в терминале Som, `somcat` — эталонный клиент.

Этот документ фиксирует все значимые архитектурные и технические решения по ходу реализации — не туториал, а рабочий журнал решений с обоснованием "почему", чтобы не терять контекст между сессиями.

**Статус: транспорт И paint-путь полностью работают end-to-end через реальный ConPTY, живьём подтверждены GIF/JPEG/PNG с правильными размерами, цветами, курсором после картинки, корректным clear/scroll и фокусом ввода после старта.** Печать placeholder-грида переехала из Som в `somcat` (клиент печатает через свой реальный stdout, не через `write_output` — устраняет рассинхронизацию курсора с реальным shell'ом), добавлена поддержка JPEG/PNG, исправлена обрезка/сжатие при частичном скролле, реализован активный пересчёт placement'ов при ресайзе окна/шрифта в ОБЕ стороны (рост и сжатие по ширине и высоте, включая вставку/удаление строк с сохранением нижележащего контента) — см. соответствующие секции ниже. **Аудио (mp3/flac) реализовано с прогрессивным декодированием+воспроизведением** (виджет и звук стартуют от того префикса файла, что уже докачан, не после полной докачки — критично для многогигабайтных FLAC), поверх нового общего Som→client query/response-канала (byte-range seek за пределы закэшированного — первый конкретный потребитель, не единственный запланированный); виджет закрываем (крестик реально удаляет placeholder-строку), `clear` останавливает всё играющее в табе аудио — см. "Прогрессивное аудио + общий query/response-канал" ниже.

## Зачем свой протокол, а не Kitty (историческое обоснование)

Измерено на момент принятия решения: Kitty-путь (PNG-перекодирование каждого кадра + base64 через APC) для 47-кадрового GIF 256×256 давал 5.3MB трафика — многосекундные паузы, неприемлемо для анимации, тем более для аудио/видео 4K60 в будущем. Причина — Kitty обязан оставаться 7-бит-safe (base64), потому что таков стандарт, которому он следует ради совместимости со сторонними клиентами.

У SRP нет такого обязательства — свой протокол, свой клиент, свой вьюер. Решено: **полностью отдельная система**, не переиспользующая ни транспорт, ни хранилище, ни paint-путь Kitty — на момент этого решения они физически делили только один и тот же PTY-канал (разные marker-байты). Позже (см. "Kitty Graphics Protocol вырезан") Kitty был убран целиком, так что вопрос сосуществования больше не актуален — но исходное обоснование независимого транспорта остаётся верным описанием того, почему SRP был спроектирован с нуля, а не как расширение Kitty.

## Модель передачи: progressive file copy

Клиент (`somcat <file>`) копирует РЕАЛЬНЫЙ файл побайтово, без перекодирования кадров, chunk-за-chunk, в локальный кэш-файл на машине, где физически работает Som. Плеер начинает декодирование/показ до того, как файл докачан целиком.

Транспорт живёт целиком внутри PTY (никаких новых TCP/UDP портов, никаких сокетов в обход PTY) — работает через существующий SSH-канал (порт 22) без дополнительной инфраструктуры, включая som-tmux relay "бесплатно" (som-tmux уже прозрачно релеит любые APC-байты, а также любой другой PTY-вывод — никакой SRP-специфичной логики на стороне relay не требуется).

## VTE-патч: полный 8-бит APC

**Файл:** `errordnk/vte` (форк, локальный клон `C:\home\dnk\vte-fork-work`), коммит `649d0a6`. `errordnk/alacritty` обновлён на новый vte-rev, коммит `c9f86ad4`. `som`'s `Cargo.toml:151` — `rev = "c9f86ad4"`.

Оригинальный (непатченый) `advance_apc_string` пропускал только `0x00-0x17,0x19,0x1C-0x7E` (7-бит ASCII минус `0x18,0x1A,0x1B`) — весь диапазон `0x80-0xFF` молча терялся, `0x9C` (8-bit ST) обрывал строку, `0x7F` (DEL) молча терялся.

**Патч**: `advance_apc_string` теперь пропускает через `apc_put` ЛЮБОЙ байт кроме `0x1B` (единственный terminator, как и раньше — `ESC \`). `0x18/0x1A` (CAN/SUB — историческая VT100 семантика "оператор прерывает застрявшую escape-последовательность вручную") тоже разрешены как данные — для протокола, где отправитель это программа, а не человек за клавиатурой, этот класс сигналов не нужен. `0x9C` (8-bit ST) убран как терминатор — SRP всегда использует 7-битный `ESC \`.

Риск патча минимален: изменение изолировано в одной маленькой функции, вызываемой только в состоянии `State::ApcString` — весь остальной парсинг (CSI/OSC/Escape/Ground) не затронут.

**Важная оговорка, найденная позже**: этот патч решает проблему только для парсера ВНУТРИ Som (VTE), но НЕ решает проблему на уровне самой Windows-консоли — см. секцию "КРИТИЧНО: реальный ConPTY реинтерпретирует сырые байты через кодовую страницу" ниже. Обе проблемы независимы; патч VTE был необходим, но не достаточен.

## КРИТИЧНО: реальный ConPTY реинтерпретирует сырые байты через кодовую страницу — почему протокол ушёл от raw binary к base91

### История вопроса

Первоначальный дизайн протокола посылал `payload` как сырые бинарные байты файла (без кодирования), полагаясь на патченый VTE-парсер (см. выше), который пропускает через APC-строку любой байт кроме `0x1B`. Это работало безупречно при прямой инъекции в парсер через `Terminal::write_output` (без реального дочернего процесса/ConPTY) — файл реконструировался байт-в-байт.

**Но реальный `somcat --stream`, запущенный как настоящий дочерний процесс через настоящий ConPTY pseudo-console, systematically повреждал данные.** Диагностика заняла много времени, потому что на первый взгляд всё выглядело так, будто все конверты успешно доходят до парсера (`log::trace!`/`eprintln!`-диагностика подтверждала: количество успешных "chunk parsed" срабатываний точно совпадало с количеством отправленных чанков) — то есть проблема казалась не в транспортном уровне, а где-то дальше.

### Найденная причина

Windows ConPTY — это НЕ прозрачный байтовый pipe для stdout дочернего процесса. На другом конце трубы стоит `conhost.exe`/`OpenConsole.exe`, реализующий полноценный **текстовый** терминальный буфер (character-cell based), а не байтовый. Он интерпретирует сырой поток байтов дочернего процесса через **активную консольную output-кодовую страницу** (например CP866 — кириллица DOS, что и оказалось активным на диагностической машине), после чего перекодирует получившийся текст обратно в UTF-8 для передачи через свой собственный VT-канал, который уже читает `alacritty_terminal`'s PTY-ридер.

Любой байт `>= 0x80` в исходном потоке реинтерпретируется как символ активной кодовой страницы и переотправляется как многобайтовая UTF-8 последовательность (обычно 2-3 байта на исходный 1 байт) — что и объясняло систематическое расхождение `declared_len < actual_len` в диагностике (например `declared 76, actual 129`).

Это **подтверждено экспериментально дважды, полностью изолированно от протокола SRP**:
1. Крошечный 8-байтовый фикстур с известными high-байтами (`c0 80 81 82 ff fe`), отправленный через `somcat --raw85`/`--raw91` (временные diag-режимы) в реальный ConPTY, показал: каждый байт `>= 0x80` превращался в 2-3 байта на приёме, соответствующие CP866-транслитерации этого байта, перекодированной в UTF-8.
2. Переключение `SetConsoleOutputCP(65001)` (UTF-8) НЕ решило проблему — оно лишь сменило форму искажения: произвольные байты не являются валидным UTF-8, поэтому невалидные последовательности заменялись на `U+FFFD` (REPLACEMENT CHARACTER, 3 байта в UTF-8) — по одному на каждый повреждённый исходный байт. Расширение размера осталось.

Это системное поведение Windows-консоли, находящееся полностью вне контроля `alacritty_terminal`/патченого VTE-парсера. Единственный надёжный способ обойти его — никогда не помещать байт `>= 0x80` (и вообще ничего, что кодовая страница могла бы реинтерпретировать) на wire.

Забавное следствие: получается, что base64/подобные text-safe кодировки нужны терминальным графическим протоколам не ТОЛЬКО из-за исторического 7-битного ограничения VTE-парсеров (что мы изначально предполагали и патчили) — это ограничение оказалось необходимым ещё и для выживания через саму Windows-консоль, причём патч VTE тут не помогает вообще.

### Выбор алфавита кодирования: base64 → base85 → base91

Раз весь payload должен состоять только из "безопасных" байтов, следующий вопрос — какой алфавит минимизирует оверхед. Три варианта проверены байт-в-байт через реальный ConPTY (не расчётом, а прогоном полного диапазона `0x00-0xFF` через настоящий `somcat`-подпроцесс и сверкой результата):

| Кодировка | Алфавит | Оверхед | Результат теста через реальный ConPTY |
|---|---|---|---|
| base64 | `A-Za-z0-9+/=` | ×1.33 | не тестировался напрямую (уже известный стандарт) |
| base85 (ASCII85-подобный) | `!`..`u` (0x21-0x75) | ×1.25 | **byte-perfect**, подтверждено |
| base91 | 91 символ из `0x21-0x7E` минус `"`, `'`, `\` | ×1.23 | **byte-perfect**, подтверждено |

Выбран **base91** — наименьший оверхед из проверенных вариантов, при этом полностью надёжен. Причина, почему сам диапазон `0x21-0x7E` (94 символа) безопасен: это печатная ASCII-подмножество, одинаковая во ВСЕХ распространённых Windows-кодовых страницах (ASCII-совместимость в нижнем диапазоне — общее свойство всех однобайтовых Windows codepages), поэтому реинтерпретация через активную кодовую страницу — тождественное отображение для этих байтов, никакого искажения. Выше 0x7E такой гарантии уже нет (это уже область, где кодовые страницы расходятся) — экспериментально подтверждено, что base122 (используемая для UTF-8-каналов, где используются некоторые байты `>=0x80`) почти наверняка сломается по этой же причине, хотя отдельно не тестировалась (логика идентична обоим экспериментам выше).

Из 94 символов диапазона `0x21-0x7E` исключены три: `"` и `'` (общие символы кавычек в shell/JSON-контекстах — исключены на всякий случай, не потому что они реально опасны для этого канала), и `\` (специально держится подальше от терминатора протокола `ESC \`, чтобы визуально/логически не путаться с ним, хотя парсер ищет именно пару `0x1B` + `\`, не голый `\`). Оставшиеся 91 символ и формируют алфавит.

**Файл:** `crates/terminal/src/rich_content_transport.rs`, константа `BASE91_ALPHABET` (вычисляется программно через `const fn`, не набирается руками — чтобы исключить ошибку ручной транскрипции).

## Формат конверта (актуальный, base91)

```
[marker:            1 byte  = b'S']
[header_b91:        base91-кодированные поля заголовка — см. ниже]
[separator:         1 byte  = 0x20 (пробел)]
[payload_b91:       base91-кодированный сырой payload]
```

Заголовок (до base91-кодирования):
```
[version:           1 byte  = 1]
[content_type:      1 byte  = ContentType as u8]  // 0=Gif, 1=Audio, 2=Markdown, 3=Video (резерв)
[session_id:        4 bytes LE]
[file_id:           4 bytes LE]
[chunk_offset:      8 bytes LE]
[chunk_len:         4 bytes LE, длина СЫРОГО (до кодирования) payload]
[total_size:        8 bytes LE, 0 = неизвестен]
[metadata:          18 bytes, закодированный ContentMetadata — см. ниже]
[crc32:             4 bytes LE, над СЫРЫМ payload]
```

`chunk_len`/`crc32` всегда описывают сырые байты файла, не их закодированный на wire размер — `RichContentCache` и весь downstream-код (декодер GIF и т.п.) работают исключительно в терминах реальных байт файла и вообще не знают о существовании base91-кодирования.

Отправляется как `ESC _ S <header_b91> <SEPARATOR> <payload_b91> ESC \`.

### `ContentMetadata` — типизированные метаданные по типу контента

Изначальная реализация natural-size footprint добавила плоские поля `width_px`/`height_px`/`color_bits`/`is_animated` прямо в общий заголовок, единые для всех `ContentType`. **Решено, что это неверно**: у каждого типа медиа свой набор осмысленных параметров — изображение (ширина/высота/битность/анимированность), аудио (частота дискретизации/каналы/битность сэмпла), видео (ширина/высота/fps/кодек), markdown (вообще без геометрии). Плоская схема заставила бы каждый чанк таскать неиспользуемые поля чужих типов.

**Решение**: `pub enum ContentMetadata` с вариантом на каждый смысловой набор метаданных (`Image { width_px, height_px, color_bits, is_animated }`, `Audio { sample_rate, channels, bits_per_sample }`, `Video { width_px, height_px, fps_numerator, fps_denominator, codec: VideoCodec }`, `Markdown` без полей). `ContentType::Gif` (и в будущем PNG/JPEG) маппится на `ContentMetadata::Image` — Image описывает растровые данные вообще, не конкретно GIF.

Кодирование в заголовке — фиксированной длины (1 байт discriminant + 17 байт полей, дополненных нулями до размера самого большого варианта — `Video`), а не переменной: все поля вариантов — фиксированного размера целые числа (без `Vec`/строк), так что паддинг до максимума проще, чем городить ещё один SEPARATOR-подобный механизм для метаданных отдельно от того, что уже нужен для header/payload границы (см. секцию ниже) — в отличие от `payload`, длина метаданных не варьируется от содержимого, поэтому здесь фиксированная длина не создаёт той же проблемы, что решал SEPARATOR для base91-кодированного payload.

`fps_numerator`/`fps_denominator` (не единое float/round-число) — потому что видео-контейнеры сами часто выражают частоту кадров как рациональное число (NTSC 30000/1001) — так не теряется точность при конвертации из/в то, что реально отдаёт декодер, когда видео будет реализовано.

**Файл:** `crates/terminal/src/rich_content_transport.rs`, `ContentMetadata`/`VideoCodec` enums, `encode_metadata`/`decode_metadata` функции.

### Почему нужен байт-разделитель между header и payload

Изначальная (не base91, а промежуточная hex-кодированная) версия протокола полагалась на ФИКСИРОВАННУЮ длину закодированного заголовка, чтобы находить границу header/payload по простому byte-offset. Это работало для hex-кодирования (2 hex-символа на байт, всегда фиксированное соотношение), но **не работает для base91**: basE91's битовая упаковка потребляет 13 или 14 бит на пару выходных символов В ЗАВИСИМОСТИ ОТ КОНКРЕТНЫХ БИТОВЫХ ЗНАЧЕНИЙ данных, а не только от их количества — значит закодированная длина одного и того же по размеру, но разного по содержимому заголовка может быть разной в разных случаях. Фиксированного byte-offset для header/payload границы просто не существует (в отличие от самого `ContentMetadata`, где длина фиксирована паддингом — см. выше).

Решение: литеральный байт-разделитель `0x20` (пробел) между `header_b91` и `payload_b91`. Он безопасен как разделитель именно потому, что лежит НИЖЕ нижней границы base91-алфавита (`0x21`) — ни при каких обстоятельствах не может встретиться внутри корректно закодированных данных, поэтому `parse_envelope` ищет первое вхождение `0x20` после marker-байта и режет конверт по нему однозначно.

## Почему больше не нужен byte-stuffing (`TrailingByte`) — историческая деталь

**Более ранняя версия протокола** (до перехода на base91) полагалась на raw-binary payload с `0x1B` в качестве единственного запрещённого байта, а после обнаружения ConPTY CRLF-искажения (Windows ConPTY вставляет `\r` перед КАЖДЫМ голым `\n` в выводе дочернего процесса, подтверждено доккомментарием `alacritty_terminal::event_loop::EventLoop::collapse_cr_cr_lf`) — расширила запрет на `0x1B` И `0x0A`, с механизмом `Chunk::trailing_byte: Option<TrailingByte>` (byte-stuffing: опасный байт исключается из `payload`, передаётся отдельным полем заголовка, получатель дописывает его в файл вручную) и функцией `split_into_chunks`, которая резала исходные данные перед каждым таким байтом.

**После перехода на base91-кодирование ВСЕГО payload вся эта машинерия стала не нужна** — раз каждый байт на wire гарантированно принадлежит 91-символьному "безопасному" алфавиту, внутри payload нет и не может быть ни `0x1B`, ни `0x0A`, ни какого-либо другого потенциально опасного байта, независимо от того, что реально лежит в исходном файле. `split_into_chunks` теперь — тривиальная нарезка по фиксированному размеру (`data.chunks(max_len)`), `Chunk` больше не имеет поля `trailing_byte`.

## КРИТИЧНО: std::io::Stdout::flush() виснет на Windows/ConPTY с бинарными данными

**Симптом**: `somcat --stream` намертво зависал в реальном ConPTY-тесте (headless `#[gpui::test]`), но работал мгновенно при простом файловом pipe-редиректе — разница ставила в тупик несколько итераций диагностики.

**Корень**: `std::io::Stdout` на Windows оборачивает handle в `LineWriter`, который флашит внутренний userspace-буфер только до последнего увиденного `\n` (0x0A). Бинарный/закодированный SRP-конверт почти никогда не содержит настоящий `\n` (тем более после перехода на base91 — алфавит вообще не включает `0x0A`). `write_all()` сам по себе возвращал `Ok` (данные просто копились в буфере), но explicit `.flush()` СРАЗУ ПОСЛЕ него блокировался навсегда на первом же чанке (113 байт) — воспроизводилось стабильно 100% раз.

**Решение**: `write_raw_stdout()` — на Windows пишет напрямую через `WriteFile` (Win32 API) на `STD_OUTPUT_HANDLE`, полностью обходя `std::io::Stdout`/`LineWriter`. На Unix обычный `write_all` (там `LineWriter`-проблемы для pipe/pty-таргета нет).

**Файл:** `crates/somcat/src/main.rs`, функция `write_raw_stdout`.

## Клиентский режим: somcat

`somcat <file>` (или явно `somcat --srp <file>`) — не требует `raw_mode::enable()` полностью (нет query/negotiation — SRP не optional-with-fallback внешний стандарт), но требует `raw_mode::enable_output_vt_processing()` (устанавливает `ENABLE_VIRTUAL_TERMINAL_PROCESSING` только на output-handle, не трогая stdin — вариант, трогающий stdin, падал с "handle is invalid" при отсутствии реального stdin TTY).

Content-type определяется по расширению файла (`.gif` → `ContentType::Gif`, остальное пока не реализовано).

`gif_metadata()` в `crates/somcat/src/main.rs` извлекает `ContentMetadata::Image` перед стримингом: ширина/высота через `ImageDecoder::dimensions()` (читает только фиксированный logical screen descriptor, не декодирует ни одного кадра), `is_animated` — быстрым байтовым сканом сырых байт файла на наличие ВТОРОГО Image Descriptor блока (`0x2C`) вместо полного декодирования всех кадров через `AnimationDecoder::into_frames()` (было бы расточительно только ради подсчёта кадров на большом файле). Не строгий GIF-парсер (не проходит extension-блоки байт-в-байт), но `0x2C` не может легитимно встретиться как байт данных до первого настоящего Image Descriptor в реалистичных GIF-файлах, так что это надёжная эвристика.

## Серверная сторона

- `crates/terminal/src/rich_content_cache.rs` — `RichContentCache`: progressive on-disk writer с watermark-трекингом (`contiguous_len`), поддержка out-of-order чанков через `pending_ranges`. Путь кэша: `paths::config_dir().join("media_cache")` в production, `std::env::temp_dir()` в тестах (`paths::config_dir()` — process-global `OnceLock`, не test-aware).
- `crates/terminal/src/rich_content_gif_player.rs` — `try_decode_progressive`: инкрементальный GIF-декод по мере роста файла. **Важная находка**: `gif` crate's `DecodingError::UnexpectedEof` НЕ оборачивает `std::io::Error` (`source()` возвращает `None`) — приходится матчить по тексту "Unexpected End of File", не по типу ошибки.
- Роутинг в `Terminal::process_event` (`crates/terminal/src/terminal.rs`): проверка `bytes.first() == Some(rich_content_transport::MARKER)` — единственная интерпретация APC-строк, которую Som сейчас реализует (после удаления Kitty).

## Ключевой диагностический паттерн: изоляция транспорта от реального ConPTY

Тест `test_rich_content_many_real_chunks_via_write_output_reconstructs_file_exactly` (`crates/terminal/src/terminal.rs`) — прогоняет ВСЕ реальные чанки настоящего GIF-файла через `Terminal::write_output` НАПРЯМУЮ (прямая инъекция в VTE-парсер, без дочернего процесса, без ConPTY вообще), реконструирует файл с диска и сверяет байт-в-байт с исходником. Выполняется за доли секунды вместо 15-секундного таймаута через реальный процесс.

Этот тест оказался ключевым диагностическим инструментом дважды: сначала подтвердил, что CRLF-искажение `write_output`'s LF→CRLF конвертации ломает бинарный payload (что впоследствии решено переходом на `TrailingByte`, а затем полностью снято переходом на base91), а затем — что после перехода на base91 транспортный уровень абсолютно корректен САМ ПО СЕБЕ, что сузило поиск бага исключительно до реального ConPTY-специфичного поведения (не до логики парсинга/сборки конвертов).

**Важно помнить, если снова возникнет похожая проблема**: `write_output` (прямая инъекция) и реальный дочерний процесс через ConPTY — это ДВА РАЗНЫХ пути с разным поведением на Windows. Тест, "проходящий" через `write_output`, не гарантирует, что тот же самый байтовый поток переживёт реальный ConPTY — именно это разделение и позволило точно локализовать ConPTY-кодовую-страницу-реинтерпретацию как корневую причину, а не искать баг в парсере/протоколе.

## Paint-путь v1 (anchor/cursor-relative) — заменён, историческая справка

Первая рабочая версия анкорила placement к позиции курсора в момент первого чанка (`CacheEntry::anchor: (i32, usize)`, тот же паттерн, что Kitty's cursor-relative `a=p` placement), с paint-математикой, компенсирующей рассинхронизацию anchor'а от `Grid::history_size()` дельты. Живым тестом (2026-08-10) подтверждено: анимация видна, natural-size footprint корректен, RGBA→BGRA конверсия даёт правильные цвета — но пользователь отверг сам ПОДХОД: "какими-то кривыми хаками добиваться сдвига курсора, инпута и прочего скролла, нужно чтобы в основе своей терминал воспринимал картинку как блок текста". Три требования (clear прячет картинку, курсор после картинки, плавный скролл) требовали bespoke-математики поверх anchor'а вместо использования уже существующего текстового механизма терминала — решено переписать целиком на unicode-placeholder-grid архитектуру (см. ниже), той же самой, что Kitty Stage 4 уже использовал для СВОЕГО unicode-placeholder режима.

## Paint-путь v2 (unicode-placeholder grid) — текущая реализация

Картинка представлена как N×M реальных ячеек терминального грида, каждая содержит специальный placeholder-символ (`U+10EEEE`) плюс 1-2 комбинирующие диакритики, кодирующие row/column этой ячейки внутри placement'а (297-элементная таблица `ROWCOLUMN_DIACRITICS`, `crates/terminal/src/kitty_graphics_placeholder.rs` — общий модуль, изначально написанный для Kitty Stage 4, переиспользуется SRP как есть). `(session_id, file_id)` кодируется в fg/underline-цвет ячейки (`\x1b[38;2;r;g;bm`/`\x1b[58;2;r;g;bm`), 24-битная RGB-кодировка `u32`.

**Ключевое отличие от anchor-подхода**: эти ячейки печатаются через ОБЫЧНЫЙ VTE-путь (как реальный текст), то есть `Term`'s grid трактует их как настоящий контент — scroll/clear/курсор работают через уже существующий, ничем не модифицированный механизм терминала, без anchor/history_size математики вообще. `clear` прячет картинку просто потому что она — часть очищенного текста; курсор естественным образом оказывается после напечатанного блока; скролл двигает картинку вместе с текстом, потому что это и есть текст.

`CacheEntry` (`rich_content_cache.rs`) больше не хранит `anchor`/`anchor_history_size` — актуальное состояние: `content_type`, `total_size`, `max_column_seen` (см. "Печать грида переехала в somcat" и "Фикс обрезки/сжатия при частичном скролле" ниже).

### Печать грида переехала из Som в somcat (архитектурный переход)

Изначальная реализация Paint-путь v2 печатала placeholder-грид ИЗ Som, через `Terminal::print_rich_content_placeholder_grid` → `self.write_output()`, при завершении SRP-стрима. Это работало для отображения, но **ломало реальный интерактивный ввод**: `write_output` инжектирует байты напрямую в локальную VTE-модель терминала Som, МИНУЯ реальный PTY/ConPTY-канал. Реальный shell (PowerShell/PSReadLine) на другом конце PTY ничего не знает об этой инъекции — его собственная модель курсора не сдвигается, и при следующей перерисовке строки (например, при начале ввода следующей команды) PSReadLine перерисовывает от СВОЕЙ устаревшей позиции курсора, "утаскивая" курсор обратно наверх, поверх картинки. Живой тест подтвердил симптом дословно: "курсор сдвигается, но нужно сдвинуть ещё на одну строку, и `~` не сдвигается, как и не сдвигается инпут ввода, как только начинаю печать, то курсор убегает наверх".

**Решение**: печать грида переехала в САМ `somcat` — клиент теперь печатает placeholder-текст через свой РЕАЛЬНЫЙ stdout (`write_raw_stdout`, прямой `WriteFile`), то есть через тот же самый PTY-канал, через который идёт весь остальной вывод дочернего процесса. С точки зрения shell'а это неотличимо от того, как если бы любая другая программа напечатала текст — никакой рассинхронизации курсорной модели, никаких хаков.

Это потребовало, чтобы `somcat` сам знал реальные метрики терминала (не полагаясь на то, что Som их знает и печатает сам):
- **`query_cell_size_px()`** — шлёт `CSI 16 t` ("report cell size in pixels"), парсит ответ `\x1b[6;{height};{width}t`. Som отвечает на этот запрос через уже существующую инфраструктуру `alacritty_terminal::Term::cell_size_pixels` → `Event::TextAreaSizeRequest` → `Terminal::process_event`'s обработчик.
- **`query_cell_count()`** — шлёт `CSI 18 t` ("report text area size in characters"), парсит ответ `\x1b[8;{lines};{cols}t` (через тот же `TextAreaSizeRequest`-путь, `alacritty_terminal::Term::text_area_size_chars`). Нужен отдельно от `query_cell_size_px()`, см. следующую секцию.
- `raw_mode::enable()` (в `crates/somcat/src/raw_mode.rs`) — полноценный RAII terminal-raw-mode guard (не только `enable_output_vt_processing()`, как раньше): `ENABLE_VIRTUAL_TERMINAL_INPUT` на stdin (нужно, чтобы прочитать `CSI 16 t`/`CSI 18 t`-ответы с stdin) + `ENABLE_VIRTUAL_TERMINAL_PROCESSING` на stdout + `SetConsoleOutputCP(65001)` (см. следующий абзац).

**Побочная находка**: после переноса печати в somcat живой тест показал видимый текстовый "мусор" на экране вместо placeholder-грида. Причина — то же самое ConPTY-кодопейдж-реинтерпретация, что уже задокументирована выше для транспортного payload (см. "КРИТИЧНО: реальный ConPTY реинтерпретирует сырые байты через кодовую страницу"), только теперь применительно к САМОМУ placeholder-тексту: он не base91-кодирован (это реальный многобайтовый UTF-8 текст, не оверлей поверх payload), и ConPTY реинтерпретировал байты `>=0x80` через активную консольную output-кодовую страницу. Решено явным `SetConsoleOutputCP(65001)` внутри `raw_mode::enable()`.

### Единицы измерения: физические пиксели картинки vs логические (DIP) пиксели GPUI

Важная деталь, из-за которой картинка на HiDPI/4K-экранах (с DPI-scale ≠ 1.0) изначально отображалась неверно (обрубком в углу экрана): `width_px`/`height_px` картинки (из `ContentMetadata::Image`, извлечённые декодером формата — `image::ImageReader::into_dimensions()` для JPEG/PNG, `GifDecoder::dimensions()` для GIF) — это РЕАЛЬНЫЕ ФИЗИЧЕСКИЕ пиксели файла. А `cell_width`/`cell_height`, которые Som отвечает на `CSI 16 t`, — это GPUI's ЛОГИЧЕСКИЕ (DIP) пиксели, не зависящие от DPI-scale монитора (GPUI абстрагирует физические пиксели экрана единообразно). Деление одних на другие даёт `columns`/`rows`, завышенные ровно в `scale_factor` раз при DPI-scale > 1.0 — placeholder-грид получался шире, чем реальная ширина терминала в колонках, и терминал молча переносил его посередине строки (`wrapline`), скрещивая закодированные row/column-координаты каждой ячейки с их реальной позицией на экране.

**Фикс**: `somcat`'s `print_placeholder_grid` дополнительно вызывает `query_cell_count()` и клэмпит `columns` по реальному числу колонок терминала, масштабируя `rows` пропорционально (сохраняя аспект картинки), если пришлось урезать по ширине. **Обновлено (2026-08-12, по прямому требованию)**: `rows` ТОЖЕ клэмпится — до `terminal_rows - 1`, не просто `terminal_rows` — так что после картинки ВСЕГДА остаётся минимум одна реальная строка под приглашение шелла, а не только по ширине; картинка должна умещаться в окне целиком по обеим осям сразу, без необходимости скролла. Раньше высота намеренно НЕ клэмпилась ("избыточная высота не портит грид, просто скроллится") — это было сознательным решением для первой версии, но противоречит требованию "показывать картинку полностью с промптом внизу", поэтому пересмотрено. Та же логика продублирована в `Terminal::resync_rich_content_placements` (см. ниже) — картинка должна оставаться клэмпнутой по высоте не только при первой печати, но и на КАЖДОМ последующем ресайзе.

### Фикс обрезки/сжатия при частичном скролле

Исходная версия `paint_rich_content_placements` вычисляла bounding box картинки из min/max координат ТЕКУЩИХ ВИДИМЫХ ячеек placeholder-группы — что давало нестабильный, "прыгающий" результат при частичном скролле: когда часть картинки уходила за экран, оставшиеся видимые ячейки давали ЗАНИЖЕННЫЙ bounding box, и картинка визуально сжималась/обрубалась вместо простого клиппинга.

**Фикс, часть 1 (origin)**: origin картинки теперь вычисляется через декодированные `row`/`column` от ЛЮБОЙ ОДНОЙ видимой ячейки — `origin_line = grid_line - decoded.row`, `origin_column = grid_column - decoded.column`. Это даёт стабильный абсолютный якорь независимо от того, какая именно часть картинки сейчас видна; фактическая обрезка идёт через уже существующий верхнеуровневый `content_mask`, не через самодельную математику.

**Фикс, часть 2 (ширина/columns)**: аналогичная проблема была и с шириной — `columns` пересчитывался из максимума видимых на ТЕКУЩЕМ кадре колонок (`max_columns` локальная переменная), что тоже занижалось при частичной видимости. Решение: `RichContentCache::record_max_column_seen`/`max_column_seen` — `CacheEntry` хранит `max_column_seen: Cell<u32>`, растущий МОНОТОННО (никогда не уменьшается) по мере того, как paint-проходы сканируют всё более широкие колонки грида; `Terminal::record_rich_content_max_column_seen`/`rich_content_max_column_seen` — публичные проброс-методы для `terminal_view`. `paint_rich_content_placements` берёт `columns` из этого накопленного максимума вместо пересчёта из `image_size.width / cell_width` (то самое смешение физических/логических пикселей из предыдущей секции) — таким образом `full_width = cell_width * columns` остаётся стабильной величиной, единожды установленной по факту того, что реально было напечатано.

`Terminal::rich_content_placements() -> Vec<(u32, u32, Arc<RenderImage>, usize, bool)>` — `(session_id, file_id, render_image, current_frame, is_animating)`, БЕЗ anchor вообще.

`paint_rich_content_placements` (`crates/terminal_view/src/terminal_element.rs`) сканирует `terminal.last_content().cells`, декодирует `(session_id, file_id)` через `kitty_graphics_placeholder::decode_placeholder_cell`, для каждой группы вычисляет origin (см. выше) и полагается на `max_column_seen` для ширины, находит соответствующий decoded frame и рисует его с сохранением aspect ratio.

### JPEG/PNG поддержка

`ContentType::Jpeg`/`Png` (значения 4, 5) — расширение изначально только-GIF транспорта. В отличие от GIF (который `gif` crate умеет прогрессивно декодировать по мере роста файла — см. `rich_content_gif_player.rs`), ни JPEG, ни PNG не имеют такой семантики в `image` crate: усечённый файл просто не декодируется вообще, без надёжного способа отличить "ещё не хватает байт" от "реально повреждён". Поэтому `rich_content_player::refresh_or_create` для этих двух типов ждёт `contiguous_len >= total_size` (весь файл на диске) перед вызовом `rich_content_static_image_player::decode_complete` — тот единственным кадром декодирует файл целиком через `image::load_from_memory`.

`somcat`'s `static_image_metadata()` — извлекает `width_px`/`height_px` через `image::ImageReader::with_guessed_format().into_dimensions()` (парсит только заголовок формата, не декодирует пиксели), `is_animated` всегда `false` (ни один из этих двух форматов не имеет анимационной семантики, которую SRP реализует сейчас).

## Пересчёт placement'ов при ресайзе окна/шрифта

**Проблема**: `columns` (число колонок placeholder-грида), зафиксированное `max_column_seen` в момент печати, — правильное решение для СТАБИЛЬНОСТИ размера при скролле (см. выше), но означает, что картинка не адаптируется сама по себе, если пользователь потом меняет размер окна ИЛИ размер шрифта (оба события меняют `cell_width`/`line_height`, то есть пиксельный размер ячейки, но не меняют уже напечатанный placeholder-текст — он застыл в scrollback с тем количеством ячеек, с которым был напечатан). Задача, сформулированная явно: "нужно чтобы картинки в потоке вели себя как текст, текст же терминал переверстывает в случае ресайза окна и изменении размеров шрифта" — а также при изменении `lineHeight`/`padding` в настройках Som (оба тоже меняют пиксельный размер ячейки/доступную область, тем же путём, что и обычный ресайз окна).

**Рассмотренные и отклонённые варианты**:
1. **Встроенный soft-wrap reflow terminal'а** (`alacritty_terminal::Grid::resize` с `Flags::WRAPLINE`, уже существующий бесплатный механизм для обычного текста). Технически работает для геометрии на экране, но переносит строку по ШИРИНЕ ТЕРМИНАЛА, не по ширине картинки — если окно шире картинки, она растягивается на всю ширину окна, теряя aspect ratio (число ячеек фиксировано, ширина каждой ячейки в пикселях растёт). Отклонено: картинка должна сохранять аспект и не растягиваться сверх реального размера.
2. Прямая правка ТОЛЬКО row/column-диакритик в ячейках (не самого потока символов) под уже случившийся terminal-reflow — оказалось бессмысленным без варианта 1 (reflow не даёт нужную геометрию сам по себе).

**Реализация (текущая)**: активный пересчёт на стороне Som, `Terminal::resync_rich_content_placements` (`crates/terminal/src/terminal.rs`), вызывается из `process_terminal_event`'s `InternalEvent::Resize`-ветки сразу после `term.resize(new_bounds)` (когда grid уже реально изменил размер), с новыми `cell_width`/`line_height`:
1. Сканирует ВЕСЬ буфер (`topmost_line()..=bottommost_line()`, включая scrollback, не только текущий видимый экран — см. ниже, почему это оказалось обязательным, не опциональной оптимизацией), группирует placeholder-ячейки по `(session_id, file_id)`, попутно вычисляя старую bounding box (`old_max_row`/`old_max_column` из декодированных диакритик каждой ячейки).
2. Для каждой группы, у которой в `RichContentCache::image_size_px` есть натуральные `width_px`/`height_px` (сохранены при первом чанке из `ContentMetadata::Image` — новое поле `CacheEntry::image_size_px`), пересчитывает `new_columns`/`new_rows` той же формулой, что `somcat` применяет при первой печати (см. "Единицы измерения" выше): `ceil(width_px / cell_width)`, `ceil(height_px / line_height)`, с клэмпом `new_columns` по текущей ширине терминала (`term.columns()`), масштабируя высоту при клэмпе.
3. Column count may grow OR shrink freely (клэмп только по ширине терминала — см. выше). Row count may also grow OR shrink — см. пункт 5 ниже для того, как физически освобождается/закрывается место.
4. Перезаписывает placeholder-ячейки НАПРЯМУЮ в `alacritty_terminal::Grid` через `IndexMut<Point>` (`term.grid_mut()[point] = cell`) — БЕЗ единого escape-байта, без движения курсора. `Cell` не даёт публичного способа очистить только zerowidth-диакритики без трогания `c`/`flags` (`clear_wide` тоже сбрасывает символ), поэтому ячейка пересобирается заново (`c`/`fg`/`bg`/`flags` скопированы из старой, `underline_color` через `set_underline_color`, свежие диакритики через `push_zerowidth`). Ячейки за пределами новой (уменьшенной) bounding box заменяются на `Cell::default()`; ячейки, впервые появившиеся при росте (за пределами старой bounding box), собираются заново с цветом из образцовой ячейки той же группы (`sample_cell`). Это принципиально безопаснее, чем `write_output` с курсорными escape-последовательностями (тот самый источник рассинхронизации, который уже решался переносом печати в somcat, см. выше) — прямая правка ячеек в модели терминала не имеет отношения к тому, что "думает" реальный shell о положении курсора.
5. `RichContentCache::reset_max_column_seen` перезаписывает (не растит монотонно, как обычный `record_max_column_seen`) запомненный максимум колонки под новый размер — иначе paint-путь продолжил бы использовать устаревшее значение из-за собственного анти-сжатие правила.

**Найденный и исправленный баг (scrollback-скан)**: первая версия сканировала ТОЛЬКО видимый экран (`Line(0)..screen_lines`) ради дешевизны — картинка целиком в видимой области переписывалась правильно, но живой тест показал **размер картинки, "скачущий" при КАЖДОМ скролле после ресайза** (то шире, то у́же одной и той же группы). Причина: `Grid[Point]` индексирует АБСОЛЮТНЫЙ буфер, не то, что видно на экране (`display_offset` не участвует в этой индексации) — если часть placement'а на момент resize была вне видимой области, эти ячейки НЕ переписывались и оставались со СТАРЫМИ диакритиками; при последующем скролле paint-путь декодировал из них старый column, и `record_rich_content_max_column_seen` (растёт монотонно, никогда не уменьшается) немедленно поднимал накопленный максимум обратно вверх. Исправлено расширением сканирования на весь буфер (`topmost_line()..=bottommost_line()`), чтобы вся группа переписывалась атомарно и согласованно за один проход resize.

### Вставка/удаление строк — рост и сжатие по высоте

Первая версия ограничивала `new_rows` сверху `old_rows` (только сжатие) — рост по высоте был сознательно отложен как отдельная, более рискованная задача (см. предыдущую редакцию этого документа). Живой тест сжатия показал реальный побочный эффект: между сжавшейся картинкой и приглашением шелла оставалось пустое место — простое обнуление лишних ячеек НЕ закрывало образовавшийся зазор, нижележащий контент (включая prompt/курсор) оставался там, где был напечатан изначально.

**Решено**: реализовать полноценную вставку/удаление строк, симметрично в обе стороны, с явным требованием — **ничего не должно физически теряться**, включая крайний случай переполнения scrollback (старейшие строки истории вытесняются, как при обычном выводе текста, что уже ограничено `MAX_SCROLL_HISTORY_LINES = 100_000`, применяется через `.min(...)` во всех местах создания `Config` — settings.json не может поднять реальный лимит выше этого значения).

**Сжатие (`old_rows > new_rows`)**: `Grid::scroll_up(&(Line(origin_line + new_rows)..Line(bottommost+1)), removed_rows)` — узкий регион СРАЗУ ПОСЛЕ нового (уменьшенного) низа картинки до конца буфера сдвигается вверх, закрывая зазор; курсор, если он был ниже удалённого региона, двигается вручную на `removed_rows` вверх (`Grid::scroll_up` двигает только содержимое ячеек, не знает о курсоре — в отличие от `Handler::delete_lines`, который для этой цели непригоден, потому что анкорит регион к ТЕКУЩЕЙ строке курсора, а не к позиции картинки).

**Рост (`new_rows > old_rows`)**: готового `Grid`-API для "вставить N строк в произвольной точке буфера, не двигая то, что выше" не существует — `scroll_up`/`scroll_down` всегда двигают ВЕСЬ указанный регион целиком, включая саму картинку, если она внутри региона (несколько неверных вариантов с комбинацией `scroll_up`+`scroll_down` перепроверялись на конкретных числовых примерах и каждый раз ломались на конкретных случаях — см. историю итераций в разработке). Реализована **двухэтапная вставка**:
1. `Grid::scroll_up(&(Line(0)..Line(bottommost+1)), inserted_rows)` — ВЕСЬ экран (включая саму картинку) сдвигается вверх на `inserted_rows`, освобождая место внизу и наращивая историю (то, что физически "выпадает" сверху, безопасно уходит в scrollback тем же механизмом, что и обычная печать текста). Это также означает, что `origin_line` и координаты каждой уже найденной placeholder-ячейки (`cells`) требуют пересчёта на `-inserted_rows` СРАЗУ после этого шага — забытый на первой итерации пересчёт `origin_line` был отдельным найденным багом (см. ниже).
2. **Ручная построчная вставка**: строки от конца буфера вниз до (уже скорректированного) старого низа картинки (`old_bottom = origin_line + old_rows`, после шага 1) копируются на `inserted_rows` позиций ниже, начиная с САМОЙ НИЖНЕЙ строки и двигаясь вверх (чтобы не затереть данные до того, как они прочитаны) — `Row<Cell>: Clone`, копирование через `term.grid()[Line(i)].clone()` → `term.grid_mut()[Line(j)] = row`. Освободившиеся строки `[old_bottom, old_bottom+inserted_rows)` обнуляются под новые ячейки картинки; курсор, уже перенесённый шагом 1, дополнительно сдвигается на `inserted_rows`, только если он сидел на/ниже `old_bottom` (иначе остаётся там, куда его унёс шаг 1).

Рост по высоте применяется **только если placement начинается на видимом экране** (`origin_line >= 0`) — placement, уже частично или полностью ушедший в scrollback на момент resize, оставляется при старом числе строк в этом случае; безопасная вставка в произвольной точке scrollback потребовала бы значительно более сложной работы с внутренним буфером, отложена как отдельная задача при реальной необходимости.

**Рост по ширине (columns)** реализован проще — просто пишет новые placeholder-ячейки правее старой границы картинки (нет аналога "вставки колонок" для горизонтального направления, в отличие от строк) — это осознанный риск затереть любой другой текст, который случайно оказался на той же строке правее картинки.

**Два реальных бага, найденных живым тестированием ПОСЛЕ первой версии этого раздела** (оба в двухэтапной вставке выше):
1. **Несогласованные координаты после `scroll_up`**: первая версия делала `scroll_up` шага 1, но забывала пересчитать `origin_line`/`cells` — весь остальной код (основной цикл переписи диакритик, генерация новых ячеек для выросшей области) продолжал писать по СТАРЫМ координатам, как будто `scroll_up` не сдвигал саму картинку. Живой симптом: между картинкой и приглашением шелла оставался необъяснимый разрыв в несколько строк — картинка технически рисовалась корректно, но не на предполагаемом месте относительно курсора/prompt'а. Исправлено: `origin_line` и каждая координата в `cells` явно пересчитываются на `-inserted_rows` сразу после `scroll_up`.
2. **Паника при выталкивании строк за пределы экрана**: построчная копия (шаг 2) писала `term.grid_mut()[Line(target)] = row` без проверки `target <= bottommost_line()` — на маленьком экране, где рост сдвигает часть строк ЗА нижний край видимой области, это индексирует `Grid` за пределами реально существующих строк и паникует. Живой симптом: реальный краш всего процесса Som при разворачивании небольшого окна на весь экран сразу после показа картинки (подтверждено логом, обрывающимся сразу после записи `Resizing:`/`New num_cols...`, без единого дальнейшего сообщения). Исправлено: `if target <= bottom { ... }` — шаг 1 уже безопасно вытолкнул содержимое ЗА эту границу в scrollback, так что пропуск такой записи на шаге 2 ничего не теряет (она уже сохранена).
3. **Слияние двух РАЗНЫХ placement'ов одной и той же картинки в одну группу**: `groups`-словарь изначально ключевался ТОЛЬКО по `(session_id, file_id)`. Если одна и та же картинка напечатана дважды (например, показана, потом показана ещё раз после того, как окно было изменено в размере) — на экране/в scrollback одновременно существуют ДВА физически раздельных блока placeholder-ячеек с одинаковым id. Каждая ячейка кодирует свой (row, column) как СМЕЩЕНИЕ от собственного верхнего левого угла блока — значит ячейка `(row=0, column=0)` первого блока и ячейка `(row=0, column=0)` второго блока декодируются ОДИНАКОВО, хотя физически находятся в разных местах grid'а. Ключуя только по id, оба блока сливались в одну группу с `cells`, вперемешку содержащими точки из ДВУХ несвязанных мест экрана — `origin_line` вычислялся из первого попавшегося (по порядку итерации HashMap) элемента, вставка/удаление строк применялись к этой каше координат, что портило grid и роняло процесс. Живой симптом: краш при развороте окна после того, как одна и та же картинка была показана дважды в разных размерах терминала — воспроизведено тестом `test_resize_growth_with_two_placement_groups_of_same_image_does_not_panic`, который сначала не проявлял баг (тест мержил оба принта в одну группу так же, как и продакшен-код, поэтому визуально "работал"), пока не была добавлена проверка фактического числа групп. Исправлено: ключ группировки расширен до `(session_id, file_id, origin_line, origin_column)`, где `origin_line`/`origin_column` вычисляются для КАЖДОЙ ячейки индивидуально (`line - row`, `column - column`) ещё на этапе скана — так два физически раздельных блока с одинаковым id гарантированно попадают в разные записи словаря, независимо от порядка обхода.
4. **Курсор не сдвигался вместе с `scroll_up`, роняя ВООБЩЕ ЛЮБОЙ следующий ресайз**: `Grid::scroll_up` (сам из alacritty, подтверждено чтением исходника) двигает только содержимое ячеек — `self.cursor.point` НЕ трогает никогда. Первая версия кода полагалась на неверный комментарий "курсор уже перенесён вместе с экраном" и НЕ двигала курсор после `scroll_up` целого экрана в блоке роста. После нескольких ресайзов подряд курсор накапливал рассинхронизацию и в итоге получал ОТРИЦАТЕЛЬНУЮ координату `Line` — на следующем вызове `term.resize()` сам alacritty падал с `attempt to subtract with overflow` (`grid/resize.rs:276`, `self.lines - self.cursor.point.line.0 as usize` — отрицательный `Line` при касте в `usize` даёт огромное число). Живой симптом (первое сообщение после фикса бага №3): "при изменении размеров сом падает" — воспроизведено (после уточнения у пользователя: 2 копии одной картинки, показанные в разных размерах окна, затем попытка развернуть) той же серией шагов, что и баг №3, но проявлялось ТОЛЬКО через несколько ресайзов подряд.
5. **Наивное суммирование двух курсорных коррекций давало неверный итог**: первая попытка исправить баг №4 сдвигала курсор на `-inserted_rows` после `scroll_up`, а затем ЕЩЁ РАЗ на `+inserted_rows` во втором (независимом) блоке коррекции — расчёт на конкретных числах (`origin_line=0, old_rows=2, inserted_rows=4` из юнит-теста) показал, что курсор оказывается на `origin_line+old_rows` вместо ожидаемого `origin_line+new_rows`, то есть КОРОЧЕ на `new_rows-old_rows` строк, чем должен быть — юнит-тест `test_resize_growing_placeholder_grid_height_pushes_down_content_printed_after_it` ловил это как `left: 4, right: 6`. Исправлено переходом на единый инвариант вместо накопления дельт: `cursor_offset_from_old_bottom` (позиция курсора относительно СТАРОГО низа картинки, захваченная ОДИН раз до всех мутаций) сохраняется и после роста восстанавливается как `new_bottom + cursor_offset_from_old_bottom` — независимо от того, сколько промежуточных операций (сдвиг экрана, затем построчная копия) потребовалось.
6. **`scroll_up` всего экрана вызывался БЕЗУСЛОВНО на `inserted_rows`, даже когда внизу и так было пусто**: на достаточно высоком экране с картинкой у самого верха вставка новых строк не требовала выталкивания контента в scrollback вообще (внизу полно свободных строк) — но код всё равно сдвигал ВЕСЬ экран (включая картинку и курсор) в scrollback, что и давало описанное выше несоответствие 4 vs 6. Исправлено: считается `spare_rows_below` (реально свободные строки под старым низом картинки) и `shift = inserted_rows.saturating_sub(spare_rows_below)` — сдвиг экрана происходит только на РЕАЛЬНО недостающее количество строк, а не всегда на полный `inserted_rows`. Построчное копирование при этом тоже должно двигать контент не на `inserted_rows`, а на `copy_distance = new_bottom - old_bottom` (эти две величины совпадают только когда `shift == inserted_rows`, то есть свободных строк не было вообще) — использование `inserted_rows` вместо `copy_distance` после этого фикса стало отдельным (уже найденным при той же диагностике) источником паники `Grid::compute_index`'s `requested.0 < visible_lines`.
7. **Координаты ЕЩЁ НЕ обработанных групп не корректировались после `scroll_up` предыдущей группы**: при ДВУХ группах одной картинки на экране (см. баг №3) группа, обрабатываемая раньше (выше на экране), может выполнить `scroll_up` всего экрана — это физически сдвигает координаты ВСЕХ ячеек, включая принадлежащие ещё не обработанной ВТОРОЙ группе, чьи `cells`/`origin_line` были один раз вычислены в скане ДО начала цикла по группам и никогда не обновлялись. Исправлено: переменная `accumulated_shift`, накапливающая суммарный `shift` каждой уже обработанной группы, применяется к координатам `cells` каждой СЛЕДУЮЩЕЙ группы перед вычислением её `origin_line`.
8. **Финальная курсорная коррекция применялась КО ВСЕМ группам без разбора, хотя курсор физически один**: когда на экране одновременно ДВЕ (или больше) группы одной картинки, курсор реально может стоять только около ОДНОЙ из них — но код применял "поставить курсор на `new_bottom` этой группы" безусловно для КАЖДОЙ обрабатываемой группы, включая ту, рядом с которой курсора никогда не было. Для "чужой" группы это отправляло курсор в произвольную (иногда за пределы экрана) позицию — на следующем `sync()`-вызове `alacritty_terminal::term::RenderableCursor::new` падал с `requested.0 < self.visible_lines` (`grid/storage.rs:221`), потому что курсор индексировал несуществующую строку. Живой симптом ("сом падает при изменении размера") воспроизведён вживую и unit-тестом `test_resize_growth_with_two_placement_groups_of_same_image_does_not_panic` только после того, как баги №3, 6 и 7 уже были исправлены — этот баг был "последним слоем" под ними. Исправлено: финальная коррекция курсора на `new_bottom` конкретной группы применяется ТОЛЬКО если курсор на момент обработки этой группы был точно на её `old_bottom` (`cursor_at_old_bottom`); безусловная часть (курсор двигается вместе со `scroll_up` целого экрана) остаётся отдельной и применяется всегда, вне зависимости от того, к какой группе относится курсор.
9. **САМ alacritty реflow'ит широкие placeholder-строки при сужении ШИРИНЫ терминала, ДО того как `resync_rich_content_placements` вообще успевает что-либо сделать** — корневая причина, найденная ПОСЛЕ багов №1–8, когда живой тест всё ещё показывал разрыв между картинкой и промптом при постепенном сужении окна мышью. `Term::resize` (стандартный alacritty API) вызывает `self.grid.resize(!is_alt, num_lines, num_cols)` — параметр `reflow=true` жёстко зашит для основного (не alt-screen) экрана, никак не настраивается через публичный API. Плейсхолдер-строки картинки — широкие ряды ячеек БЕЗ флага `WRAPLINE` (печатаются с явным `\r\n` после каждой), но когда новая ширина терминала становится МЕНЬШЕ, чем длина такой строки, `Grid::shrink_columns`'s встроенный reflow (`grid/resize.rs`, `row.shrink(columns)`) всё равно разбивает её на ДВЕ строки grid'а — это растит РЕАЛЬНОЕ число строк буфера (и, если экран заполнен, `history_size`) кода САМ ALACRITTY, вне контроля Som, ДО того как мой код успевает пересчитать placeholder-геометрию. Живой симптом, пойманный через диагностический вывод: `origin_line` картинки монотонно уходит всё глубже в отрицательные (scrollback) при каждом мелком шаге сужения ширины (`-27, -28, -29...`), синхронно утягивая курсор туда же — после накопления курсор уходит в `Line(-1)` и глубже, что на СЛЕДУЮЩЕМ `term.resize()` вызывает падение внутри самого alacritty (`grid/resize.rs:263`, `self.lines - self.cursor.point.line.0 as usize` — тот же класс бага, что и №4, но триггерящийся встроенным reflow, а не кодом Som). Регрессионный тест `test_resize_shrinking_terminal_width_in_many_small_steps_keeps_prompt_immediately_after_image` (широкая 1920×1080 картинка, окно постепенно сужается на 8px за шаг) сначала падал именно на этой панике внутри alacritty.

  **Фикс — патч форка `errordnk/alacritty` (ветка `som-disable-reflow`, коммит `fb1a87b6`)**: добавлен новый публичный метод `Term::resize_with_reflow(size, reflow: bool)`, куда вынесена вся логика прежнего `resize` — сам `resize` теперь просто зовёт его с `reflow=true` (сохраняя прежнее поведение для всех остальных вызывающих кодов, если такие появятся). Внутри `resize_with_reflow` параметр `reflow` пробрасывается в оба вызова `self.grid.resize(reflow && !is_alt, ...)`/`self.inactive_grid.resize(reflow && is_alt, ...)`. Единственный вызов `term.resize(new_bounds)` в `crates/terminal/src/terminal.rs` (`process_terminal_event`'s `InternalEvent::Resize`-ветка) заменён на `term.resize_with_reflow(new_bounds, false)`.

  **Принятый компромисс**: отключение reflow ломает автоматический перенос ДЛИННЫХ строк ОБЫЧНОГО текста при расширении/сужении терминала (например, длинная команда, набранная в широком окне, при сужении раньше переносилась бы на несколько визуальных строк — теперь просто остаётся как есть, дальше своей исходной ширины). Осознанно принято как меньшее зло: `resync_rich_content_placements` и так уже полностью пересчитывает корректную геометрию placeholder-грида с нуля при каждом ресайзе — встроенный reflow для картинок не просто не нужен, а активно вредит; для обычного текста визуальная разница минимальна (большинство терминалов и так не переносят уже напечатанный текст при последующем ресайзе, если явно не запрошено). `Cargo.toml`'s `alacritty_terminal` rev обновлён `c9f86ad4` → `fb1a87b6`.

10. **Курсор мог быть указан на строку сразу ЗА пределами экрана, если картинка выросла настолько, что заняла экран целиком** — найдено ПОСЛЕ фикса бага №9, живым тестом на короткой (43 строки) реальной высоте окна. Когда `new_bottom` (`origin_line + new_rows`) равен `screen_lines` (то есть картинка занимает вообще все строки, не оставляя ни одной под prompt), финальная курсорная коррекция (`if cursor_at_old_bottom { cursor.line = Line(new_bottom) }`, см. баг №8) указывала на `Line(screen_lines)` — на единицу БОЛЬШЕ последней реально существующей строки (`bottommost_line() == screen_lines - 1`). На следующем содержательном чтении (`Terminal::sync → make_content → Term::renderable_content → RenderableCursor::new`) alacritty индексировал `grid[point]` по этой координате и падал (`grid/storage.rs:221`, тот же класс ассерции, что и в багах №4/8, но триггерящийся уже после успешного завершения ресайза, а не во время него). Живой симптом: реальный краш, воспроизведённый пользователем через `somcat <1920×1080.jpg>` в окне, снэпнутом Win+Left/Right в половину 1536×864 (200% DPI) экрана, затем растянутом по ширине — картинка растёт по строкам вместе с ростом ширины (сохраняя аспект), и на некотором шаге доросла точно до высоты экрана. Юнит-тест `test_resize_growing_terminal_width_after_image_printed_in_a_small_window_does_not_panic` сначала не ловил баг (слишком высокие тестовые экраны, где картинка не успевала дорасти до полной высоты) — воспроизведено только после параметризации несколькими реалистичными комбинациями размера картинки/окна, включая точную геометрию этого отчёта. Первый фикс — `cursor.point.line = Line(new_bottom.min(bottom))` — защищал от краша (клэмп курсора постфактум), но не устранял саму причину: пользователь явно уточнил, что требование шире, чем "не падать" — **картинка должна помещаться в окне целиком по ОБЕИМ осям сразу, с гарантированным местом под промпт снизу, без необходимости скролла**. Финальный фикс — двусторонний клэмп на этапе вычисления `new_columns`/`new_rows` (до всей остальной логики вставки/удаления строк): после клэмпа по ширине (уже существовавшего) добавлен симметричный клэмп по высоте — `max_rows = terminal_lines - 1`, масштабируя `new_columns` пропорционально (сохраняя аспект), если высота урезана. Тот же двусторонний клэмп продублирован в `somcat::print_placeholder_grid` (там же, где раньше высота сознательно НЕ клэмпилась — "избыточная высота не портит грид, просто скроллится", что было верно ДО этого уточнения требования) — так что и самая первая печать картинки, и каждый последующий ресайз одинаково гарантируют минимум одну строку под prompt.

Диагностика багов №4–12 велась через временный свап `log::debug!` → `eprintln!` внутри `resync_rich_content_placements` и запуск `cargo test -- --nocapture` — тестовый harness не подавляет stdout, в отличие от реального процесса Som (`FreeConsole()` в `crates/zed/src/main.rs` отсоединяет процесс от родительской консоли на Windows при старте, из-за чего `eprintln!`/паника не долетают до консоли, из которой запущен `som.exe` напрямую). Для диагностики живых крашей (до появления соответствующих регрессионных тестов) `FreeConsole()` неоднократно временно закомментировалась, и запускался `RUST_BACKTRACE=full ./target/debug/som.exe` напрямую (в foreground, не в фоне через `&`) — единственный способ увидеть текст паники и backtrace живого процесса на Windows без специального дебаггера; backtrace, доходящий до `terminal::Terminal::sync`/`make_content`, а не до кода внутри `resync_rich_content_placements` напрямую, стало ключевой подсказкой, что источник — не сам вызов resize/resync, а состояние, ОСТАВЛЕННОЕ ими и прочитанное позже.

Оба направления (сжатие/рост), а также все двенадцать найденных багов, подтверждены unit-тестами в `crates/terminal/src/terminal.rs`:
- `test_resize_shrinks_placeholder_grid_to_match_new_cell_size` — базовый сценарий сжатия по ширине без текста после картинки.
- `test_resize_shrinking_placeholder_grid_height_pulls_up_content_printed_after_it` — сжатие по высоте с prompt после картинки, проверяет что prompt подтягивается вверх, зазор не остаётся.
- `test_resize_growing_placeholder_grid_height_pushes_down_content_printed_after_it` — рост по высоте с prompt после картинки на достаточно большом экране, проверяет что prompt сдвигается вниз, ничего не перезаписывается и не теряется.
- `test_resize_growing_placeholder_grid_height_past_screen_bottom_does_not_panic` — регрессионный тест на краш: экран специально высотой лишь чуть больше СТАРОГО размера картинки, рост выталкивает часть новых строк за нижний край; успех теста — сам факт, что вызов не паникует.
- `test_resize_growth_with_two_placement_groups_of_same_image_does_not_panic` — регрессионный тест на краш при слиянии групп: одна и та же картинка печатается дважды (второй раз ниже по экрану), затем терминал растится в несколько маленьких шагов подряд (имитируя покадровый drag-ресайз мышью, один вызов на пиксель движения) — успех теста в том, что обе группы остаются раздельными (проверено побочно через отсутствие паники на каждом шаге) и вызов не роняет процесс.
- `test_resize_shrinking_terminal_width_in_many_small_steps_keeps_prompt_immediately_after_image` — регрессионный тест на баг №9 (встроенный alacritty-reflow): широкая 1920×1080 картинка, терминал сужается по ширине на 8px за шаг много раз подряд, после каждого шага и в самом конце промпт должен оставаться точно на строке `final_rows` (число строк, реально занятых картинкой после клэмпа по текущей ширине) — без этого фикса тест падал ВНУТРИ самого alacritty (`grid/resize.rs:263`, отрицательный `Line` у курсора).
- `test_resize_growing_terminal_width_after_image_printed_in_a_small_window_does_not_panic` — регрессионный тест на баг №10: картинка печатается СРАЗУ в уже уменьшенном окне, затем терминал растится по ширине множеством мелких шагов (два реальных сценария: числа из более раннего лога и точная геометрия Win+Left/Right-снэпа 1536×864 экрана с 200% DPI) — на некотором шаге растущей по строкам (сохраняя аспект) картинки её высота дорастает точно до полной высоты экрана; успех теста — что ни один шаг не паникует, включая тот самый.
- `test_resize_placement_never_grows_taller_than_screen_minus_one_row` — прямая проверка требования, а не только отсутствия краша: после ресайза декодированное число строк placement'а (`placement_rows`, вычисленное из реально записанных на экране placeholder-ячеек) должно быть строго МЕНЬШЕ `screen_lines`, а курсор — строго в пределах экрана; ловит регрессию, если клэмп по высоте будет случайно убран или ослаблен в будущем, даже если сам процесс при этом не падает.

11. **Клэмп по высоте не учитывал, что placement может начинаться не с самой первой строки экрана** — `max_rows = terminal_lines - 1` вычислялся как будто ЛЮБАЯ картинка стартует с `Line(0)`, но реальный placement обычно начинается на `origin_line > 0` (например, после уже напечатанного банера/вывода шелла до картинки). Живой видео-репорт: при растягивании окна промпт корректно был виден до некоторого момента, а затем ПОЛНОСТЬЮ пропадал из виду, картинка визуально "накрывала" его — воспроизведено через живую диагностику (`log::debug!` внутри `resync_rich_content_placements`, читаемую из `~/.config/som/logs/`), обнаружившую, что на шаге, где `old_rows` вплотную подошло к абсолютному потолку `terminal_lines - 1`, `origin_line + old_rows` УЖЕ равнялось `terminal_lines` (на строку больше `bottommost_line()`), хотя формальная проверка `new_rows <= max_rows` (`45 <= 46`) проходила — потому что `max_rows` не учитывал сдвиг на `origin_line`. Исправлено: `max_rows = (terminal_lines - origin_line - 1).max(1)` при `origin_line >= 0` — реально доступное количество строк отсчитывается от фактической позиции старта картинки, а не от нуля.
12. **Курсор становился рассинхронизирован с реальным shell'ом при повторяющихся ресайзах** — самый глубокий из найденных багов, обнаруженный ПОСЛЕ фикса бага №11: даже когда курсор ВИЗУАЛЬНО был корректно привязан к нижнему краю картинки после каждого ресайза, набираемый пользователем текст появлялся в другом месте, и видимый курсор "перескакивал" туда в момент набора. Корень: `resync_rich_content_placements` напрямую правил `term.grid_mut().cursor.point.line` (введено фиксами багов №4, 5, 8, 10 выше) — это чисто ЛОКАЛЬНАЯ модель курсора в копии `alacritty_terminal::Term`, которую держит Som. Реальный дочерний процесс (PowerShell/bash), подключённый через ConPTY, ведёт СОБСТВЕННУЮ, полностью отдельную модель курсора и НИКОГДА не узнаёт о прямых правках Som-грида — API ConPTY не предоставляет операции "сдвинуть строку курсора внутри твоего внутреннего буфера", только `ResizePseudoConsole` (менять число столбцов/строк). Пока Som молчал (не печатал), визуальный курсор оставался там, где его в последний раз поставил Som, создавая иллюзию корректности — но как только реальный shell печатал ЛЮБОЙ символ (эхо набираемого текста), он писал ОТНОСИТЕЛЬНО СВОЕЙ строки курсора, которая давно разошлась с тем, что видел Som — и заметная на экране позиция ввода "прыгала" на неё. Ошибка расходования накапливалась с каждым циклом рост/сжатие, так как обе модели продолжали независимо дрейфовать. **Фикс — архитектурный**: полностью убраны ВСЕ прямые правки `term.grid_mut().cursor.point` из `resync_rich_content_placements` (три места — курсорная коррекция после `scroll_up` целого экрана, курсорная привязка к `new_bottom` после роста картинки, курсорная коррекция после `scroll_up` при сжатии). Остаются ТОЛЬКО правки содержимого ГРИДА (диакритики картинки + `scroll_up`/построчное копирование контента, включая уже напечатанный реальным текстом промпт) — те же самые операции, что терминал и так делает при обычной прокрутке большого объёма вывода, о которых shell не обязан быть уведомлён отдельно (прокрутка через переполнение экрана — штатный, всем terminals известный механизм). **Компромисс**: курсор теперь может не быть визуально идеально прижат к новому краю картинки СРАЗУ после ресайза (пока shell сам не напечатает что-то новое, восстанавливая синхронизацию естественным путём) — но он НИКОГДА не расходится с тем, что реально думает shell, и набираемый текст всегда появляется именно там, где стоит видимый курсор. Тесты `test_resize_growing_placeholder_grid_height_pushes_down_content_printed_after_it`, `test_resize_shrinking_placeholder_grid_height_pulls_up_content_printed_after_it` и `test_resize_shrinking_terminal_width_in_many_small_steps_keeps_prompt_immediately_after_image` переписаны — они проверяли `term.grid().cursor.point.line`, что было ставшей неверной проверкой самой сутью архитектуры; заменены на прямое сканирование grid'а на предмет физической позиции печатного символа `~` (первого символа промпта), что проверяет РЕАЛЬНОЕ намерение теста (текст промпта физически сдвинут вместе с картинкой), не завязываясь на курсор.

## Kitty Graphics Protocol вырезан (2026-08-10)

После перехода SRP на placeholder-grid архитектуру обе paint-функции (Kitty и SRP) оказались сканирующими ОДИН И ТОТ ЖЕ grid в поисках placeholder-текста — без протокольного разделителя между ними, только числовое id-пространство, которое могло совпасть (подтверждённый живой баг: `kitty placeholders: no stored image for id N` для реальных SRP session_id — картинка не отображалась вообще). Вместо патча коллизии решено вырезать Kitty из Som целиком — планировался отдельный addon для yazi поверх SRP, а не поддержка стороннего протокола внутри Som.

### КРИТИЧНО: RGBA→BGRA конверсия

`gpui::RenderImage` требует BGRA-порядок байт (задокументировано прямо в doc comment типа, `crates/gpui/src/assets.rs:42`), а `image::Frame`/gif-декодер отдают только RGBA. `RichContentPlayer::from_prefix` применяет построчный swap (`pixel.swap(0, 2)`) к каждому кадру `DecodedPrefix` перед созданием `RenderImage` — без этого шага цвета выходят с переставленными красным/синим каналами (подтверждено живым тестом: кожа/волосы/обивка сиденья все сдвинуты в синий).

Тест `from_prefix_converts_rgba_to_bgra` — синтетический 2-пиксельный GIF (сплошной красный + сплошной синий, построенный через `image::codecs::gif::GifEncoder` прямо в тесте, не зависит от конкретных цветов `giphy.gif`-фикстуры), проверяет точный побайтовый результат: RGBA `(255,0,0,255)` → BGRA `(0,0,255,255)` и наоборот.

**Файл:** `crates/terminal/src/rich_content_player.rs`.

## Аудио (mp3/flac) v1 — заменено прогрессивной архитектурой ниже, историческая справка

**Архитектурное решение**: декодирование (symphonia), воспроизведение (`cpal`) и сам интерактивный виджет (play/pause, seek-бар, elapsed/total время) — ВСЕ живут в Som (`crates/terminal`), не в `somcat`/клиенте.

**Почему не в клиенте (как для картинок было бы естественно предположить)**: конкретный сценарий пользователя — `somcat` может быть запущен на удалённой машине через SSH, в то время как физические колонки подключены к машине, где работает сам Som. Если бы decode+playback жили в `somcat`, звук проигрывался бы (если вообще проигрывался) на удалённой машине, а не там, где сидит пользователь. Som — единственный процесс, гарантированно локальный к пользователю, поэтому воспроизведение обязано быть его ответственностью, а не клиента.

Это единственное существенное отличие аудио-пайплайна от pattern'а картинок ("клиент решает, как рендерить контент, полученный через SRP" — верно для картинок/yazi-интеграции, НЕ верно для аудио).

**Роль `somcat`** (`crates/somcat/src/main.rs`): распознаёт `.mp3`/`.flac` → `ContentType::Audio`, читает только заголовок файла через symphonia'ный probe/format-reader (`audio_metadata()`, без полного декодирования) для заполнения `ContentMetadata::Audio { sample_rate, channels, bits_per_sample }`, стримит байты (`stream_bytes`, тот же путь что и картинки), затем печатает placeholder-грид ФИКСИРОВАННОГО размера (`print_audio_placeholder_grid`, `AUDIO_WIDGET_COLUMNS=40 x AUDIO_WIDGET_ROWS=1`) — в отличие от картинок, у аудио нет пиксельных размеров, из которых можно вывести footprint, поэтому размер зашит константой на стороне отправителя.

**Роль Som**:
- `crates/terminal/src/rich_content_audio_player.rs` — `decode_whole_file()` декодирует ВЕСЬ файл целиком в плоский interleaved `f32` PCM через symphonia (не progressive-decode как у GIF — mp3/flac не имеют чистой истории "декодируй сколько есть", поэтому паттерн ближе к JPEG/PNG-ветке "жди пока файл полностью не докачается"). `RichContentAudioPlayer::open()` открывает `cpal::default_output_device()` и запускает поток, читающий PCM через `Arc<AtomicU64>` position-курсор — стартует на паузе (не autoplay).
- `Terminal` получил отдельное поле `rich_content_audio_players: RefCell<HashMap<(u32,u32), RichContentAudioPlayer>>`, ПАРАЛЛЕЛЬНОЕ (не объединённое) с `rich_content_players` — картиночный плеер пересоздаётся заново на каждый paint-refresh, а аудио-плеер владеет живым `cpal::Stream`, чьё время жизни должно охватывать много paint-вызовов, поэтому пересоздавать его нельзя.
- Новое поле `rich_content_placement_bounds: RefCell<HashMap<(u32,u32), Bounds<Pixels>>>` — раньше НИЧЕГО не сохраняло bounds размещения между paint-вызовами (только локальные переменные внутри одного paint). Нужно для hit-testing кликов вне paint-цикла.
- `paint_rich_content_placements` (`terminal_view/src/terminal_element.rs`) получила параллельную ветку `paint_rich_content_audio_widget` — рисует quad-фон + play/pause-глиф + seek-бар (progress fill) + время через `ShapedLine::paint`, вместо `window.paint_image`.
- `Terminal::mouse_down` получил ранний перехват клика (зеркалит существующий hyperlink early-return): клик, попадающий в закэшированные bounds аудио-виджета, обрабатывается ЛОКАЛЬНО (toggle play/pause, либо seek по x-координате внутри бара) и НЕ доходит до forwarding в дочерний (возможно удалённый) процесс.
- Repaint-driving переиспользует существующий paint→force_redraw→paint self-sustaining loop (`any_rich_content_animating`), в который теперь ORится "хотя бы один аудио-плеер сейчас играет" — независимого таймера в кодовой базе как не было для GIF, так и не появилось для аудио.

**Тесты**: `crates/terminal/src/rich_content_audio_player.rs` — юнит-тесты decode/play/pause/seek на фикстуре `test_fixtures/tone.flac` (реальный `cpal`-девайс открывается по-настоящему, тест грациозно скипается в headless-окружении без устройства). `crates/terminal/src/terminal.rs::test_rich_content_audio_placement_decodes_and_plays_via_a_real_process` — полный end-to-end через реальный `somcat`-процесс + реальный ConPTY + реальный аудио-девайс, подтверждает что playback position реально продвигается после toggle play.

## Прогрессивное аудио + общий query/response-канал (2026-08-25) — заменяет предыдущую редакцию раздела выше

**Триггер пересмотра**: пользователь явно указал на дыру в только что описанной архитектуре — "а если у нас мп3 будет 4гига? или скорее всего flac, а там размеры не маленькие, мы должны начинать проигрывать еще до того как все скачалось". `decode_whole_file()`, ждущий `contiguous_len >= total_size` перед тем как вообще открыть `cpal`-поток, был приемлем только пока файлы маленькие — для реально больших файлов это означало ждать всю передачу целиком прежде чем виджет вообще появится, что противоречит уже принятому для GIF принципу "начинай показывать/играть с того префикса, что уже есть".

### Часть A: общий Som→client query/response-канал

Решение сиюминутной задачи (докачать недостающий диапазон байт для seek вперёд по ещё не докачанному файлу) потребовало того, чего у SRP раньше не было вообще — канала в ОБРАТНУЮ сторону (Som спрашивает клиента, а не наоборот). Пользователь явно потребовал НЕ делать его завязанным на аудио-range-request специфику: "двунаправленный он нужен не только для range-reqest, много для чего он нужен будет" — и раскрыл будущий мотив: **markdown станет полноценным скриптуемым интерфейсом с формами, где Lua-сценарий выполняется на той же машине, где физически лежит документ, и Som'у нужны ответы оттуда**. Соответственно спроектирован не "аудио-range-request протокол", а **типизированный, request-id-коррелируемый query-примитив**, для которого byte-range-запрос — только первый конкретный потребитель.

**Формат** (`crates/terminal/src/rich_content_transport.rs`): новый маркер-байт `QUERY_MARKER = b'Q'` (отличный от `MARKER = b'S'` обычного chunk-конверта — направление трафика меняется, поэтому и маркер другой), зарезервированный (пока не используемый) `QUERY_RESPONSE_MARKER = b'R'` для БУДУЩЕГО случая, когда ответ на запрос НЕ является естественно чанко-подобным (как раз тот самый Lua-форм-сценарий). Заголовок query (30 байт до base91): `version(1) + request_id(4) + query_type(1) + session_id(4) + file_id(4) + offset(8) + len(8)`. В отличие от обычного chunk-конверта, у query НЕТ отдельного payload-региона и SEPARATOR-байта — все поля фиксированной ширины, помещаются целиком в один base91-блок сразу после `QUERY_MARKER`. `QueryType` — enum с единственным пока значением `AudioByteRange = 0`.

**Ключевое архитектурное решение — ответ на `AudioByteRange` НЕ получил нового формата**: `RichContentCache::apply_chunk` УЖЕ умел принимать чанк, приземляющийся не по порядку, на произвольном offset (`pending_ranges: Vec<(u64,u64)>` — чанк пишется на диск по своему реальному offset, но не двигает watermark `contiguous_len`, пока разрыв не закроется) — это было спроектировано для обычной устойчивости к переупорядочиванию при доставке, просто ни разу не было реально востребовано реальным отправителем до этой задачи. Значит ответ на byte-range query — это просто ОБЫЧНЫЙ `S`-маркированный chunk-конверт, "приземляющийся не по порядку", а не новая сущность.

**Som-сторона** (`crates/terminal/src/terminal.rs`): `Terminal::request_audio_byte_range(session_id, file_id, offset, len)` строит query-конверт и пишет его через уже существующий `self.write_to_pty(bytes)` — тот же самый низкоуровневый примитив "написать байты в stdin дочернего процесса через PTY", который Som уже использует для ответа на `CSI 16 t`/`CSI 18 t` запросы клиента (`AlacTermEvent::TextAreaSizeRequest`) — просто применённый в обратном направлении. Новых механизмов писать в PTY не понадобилось.

**`somcat`-сторона** (`crates/somcat/src/main.rs`) — самая concurrency-содержательная часть новой работы: у `somcat` теперь ДОЛГОЖИВУЩИЙ фоновый поток (`spawn_audio_query_responder`), читающий собственный stdin байт за байтом в поиске `ESC _ Q ... ESC \`-конвертов, параллельно основному потоку, шлющему первичный последовательный стрим файла. Это первый случай, когда клиентский процесс читает СВОЙ ЖЕ stdin конкурентно из двух разных мест — уже существовавшие `query_cell_size_px`/`query_cell_count` делали одноразовое блокирующее чтение stdin строго ДО начала стрима, поэтому responder-поток стартует только ПОСЛЕ печати placeholder-грида, чтобы никогда не читать stdin одновременно с этими запросами. На получении валидного query с совпадающими `session_id`/`file_id` — читает нужный диапазон из уже открытого в памяти файла и шлёт его через ту же chunk-отправляющую функцию (`send_range_chunks`, теперь разделённая из бывшей `stream_bytes` на общую реализацию с параметрами `range_offset`/`range_len`), с `chunk_offset`, равным РЕАЛЬНОМУ offset в файле (не offset-от-нуля, как для первого чанка последовательного стрима).

Поскольку теперь ДВА потока (основной последовательный + responder) могут одновременно писать в stdout — `write_raw_stdout` получил `STDOUT_WRITE_LOCK: Mutex<()>`, иначе байты двух конвертов могли перемежаться на wire, что не смог бы распарсить ни `parse_envelope`, ни `parse_query_envelope`. Раньше синхронизация не требовалась вообще — у картинок/GIF никогда не было второго писателя.

### Часть B: прогрессивное декодирование+воспроизведение

`ContentMetadata::Audio` получил четвёртое поле — `duration_ms: u32`. Оно вычисляется НЕ декодированием, а из `symphonia`'s `CodecParameters::n_frames`/`time_base` (для mp3 — из Xing/VBRI VBR-тега или оценки по размеру файла, для flac — из STREAMINFO-блока), доступного сразу на этапе probe, ДО декодирования хотя бы одного семпла. Это и есть ключ к решению исходной задачи: виджет способен показать точную длительность/размер seek-бара почти мгновенно даже для многогигабайтного файла.

`rich_content_audio_player.rs` переписан почти целиком:
- `RichContentAudioPlayer::open()` больше НЕ декодирует файл целиком синхронно — вместо этого спавнит фоновый поток (`run_decode_loop`), который держит `Box<dyn FormatReader>`/`Box<dyn Decoder>` живыми между вызовами (подтверждено чтением исходника `symphonia`: `FormatReader::next_packet()` на обычном `std::fs::File` просто продолжает чтение с того места, где остановился в прошлый раз, если файл на диске с тех пор вырос — новый probe+reader после роста не требуется), декодирует новые пакеты по мере их появления и добавляет семплы в растущий `Mutex<Vec<f32>>`. При усечении файла (данных ещё не хватает) — засыпает на `DECODE_RETRY_INTERVAL = 100ms` и пробует снова, отличая "ещё не докачано, жди" от "файл целиком тут, но реально не декодируется" через сравнение с известным `contiguous_len`/`total_size`.
- `cpal`-поток открывается, как только известны `sample_rate`/`channels` (из первой же успешной пробы) — то есть почти сразу после появления первого чанка, а не после полной докачки; callback читает из растущего буфера, воспроизводя тишину за пределами того, что уже реально декодировано.
- Убрана привязка API к заранее известному числу фреймов (`known_total_frames`) — методы `position_fraction(duration_ms)`/`seek_to_fraction(fraction, duration_ms)` принимают `duration_ms` явно на каждый вызов (источник истины — `ContentMetadata::Audio`, доступный сразу с первого чанка, а не что-то, что плеер обязан знать заранее).
- **Безопасность обмена состоянием между Som (единственный писатель) и фоновым decode-потоком (единственный читатель)**: первая попытка использовала `unsafe { &*cache_ptr }` — сырой указатель на `RichContentCache`, захваченный в замыкание фонового потока. Это было отклонено ДО того, как скомпилировано/протестировано (не по ошибке компилятора, а по собственному пересмотру — паттерн некорректно полагался на гарантии времени жизни/расположения полей `Terminal`, которые типовая система реально не проверяла). Заменено безопасной альтернативой — `Arc<AudioTransferProgress>` (пара `AtomicU64`: `contiguous_len`/`total_size`), которую `Terminal` обновляет из `apply_chunk`'s call site при каждом новом чанке, а decode-поток читает только свою `Arc`-копию.

`Terminal::rich_content_audio_placements` — убран гейт `total_size == 0 || contiguous_len < total_size` (ждать весь файл), заменён на `if contiguous_len == 0 { continue; }` (виджет появляется, как только есть хоть один байт).

`Terminal::seek_rich_content_audio_playback` — при seek за пределы уже закэшированного (`target_offset > contiguous_len`) вызывает `request_audio_byte_range` (Часть A). Дедупликация через `rich_content_audio_last_range_request: RefCell<HashMap<(u32,u32), u64>>` — держащийся drag seek-бара шлёт много `mouse_drag`-событий в секунду почти на одну и ту же цель, без дедупа каждый из них порождал бы отдельный запрос; новый запрос шлётся только если цель выходит за пределы `[last_offset, last_offset + SEEK_RANGE_REQUEST_LEN)`. `SEEK_RANGE_REQUEST_LEN = 2 MiB` — запрашиваемое окно за один seek, выбрано с запасом на несколько секунд аудио даже при высоком битрейте FLAC, но не настолько большим, чтобы воссоздать проблему "жди огромную докачку" для одного seek'а.

**Живая проверка** (AutoIt burst-capture): реальный 3.3MB mp3-файл — виджет с корректной длительностью появился в пределах ~500-750мс от старта стрима (задолго до того, как файл мог докачаться целиком), клик play сразу после старта стрима дал реально звучащее и честно прогрессирующее воспроизведение (00:00 → 00:10 → 00:17 по трём последовательным скриншотам одного и того же таба, содержащего несколько инстансов теста).

### Ускорение возврата промпта, закрываемый виджет, `clear` останавливает звук (2026-08-25/26)

Три отдельных UX-запроса, найденных живым использованием уже реализованной прогрессивной архитектуры.

**Задержка перед промптом**: пользователь сообщил, что виджет теперь появляется быстро, но промпт шелла возвращается заметно позже. Диагностика (два параллельно запущенных `somcat` поверх уже играющего первого работали одновременно без проблем) исключила гипотезу "somcat блокируется/висит" — процесс и так завершался достаточно быстро, просто сама фаза синхронной отправки всех чанков файла (до возврата управления шеллу) занимала заметное время: `CHUNK_SIZE = 4096` байт означал ~800 отдельных `write_raw_stdout`-вызовов (каждый — отдельный syscall `WriteFile` под `STDOUT_WRITE_LOCK`) для типичного 3.3MB mp3, плюс ~800 отдельных событий APC-парсинга и записи в кэш на стороне Som. **Решение**: `CHUNK_SIZE` увеличен до 65536 (16x) — единственные адресаты SRP-вывода `somcat` это Som (не сторонний терминал с неизвестными ограничениями парсера), так что консервативный запас прежнего значения не был нужен.

**Ctrl+C не убивал `somcat`**: побочная находка при том же расследовании — `raw_mode::enable()` на Windows снимает `ENABLE_PROCESSED_INPUT` из режима консоли (нужно для доставки сырых escape-последовательностей на stdin), но это же и отключает системную обработку Ctrl+C как `CTRL_C_EVENT` — байт `0x03` вместо этого просто приходит на stdin как обычные данные, которые никто не проверял. Добавлена явная проверка `byte == ETX (0x03)` → `std::process::exit(130)` во ВСЕХ трёх stdin-читающих циклах `somcat` (`query_cell_size_px`, `query_cell_count`, `spawn_audio_query_responder`'s reader).

**Крестик закрытия виджета**: после `mm:ss/mm:ss` теперь рисуется `x`-глиф (`AUDIO_WIDGET_COLUMNS` увеличен с 40 до 42 — +2 колонки под глиф и его padding-клетку). Клик по нему — новая зона хит-тестинга в `handle_rich_content_click` (последняя клетка виджета), проверяется РАНЬШЕ установки `rich_content_drag` (закрытие завершает взаимодействие, тащить нечего). Первая версия просто затирала содержимое placeholder-ячеек (`Cell::default()`) — пользователь уточнил, что нужно НЕ просто очистить содержимое строки, а физически УДАЛИТЬ саму строку (сдвинуть всё нижележащее на одну строку вверх, как реальный терминальный `DL`/Delete Line), иначе после закрытия остаётся пустая строка. Реализовано новым `InternalEvent::ClearRichContentPlacement(session_id, file_id)` (обработчик мутирует грид напрямую, поэтому вызывается не из `handle_rich_content_click`, у которого нет `&mut Term`, а из `sync`'s event-дренирующего цикла, как и `InternalEvent::Clear`) — сканирует ВЕСЬ буфер (включая scrollback, виджет мог быть уже проскроллен) на предмет placeholder-ячеек нужного id, собирает затронутые строки, для каждой (снизу вверх, чтобы более ранние удаления не портили индексы ещё не обработанных) копирует каждую нижележащую строку на одну позицию выше и обнуляет освободившуюся нижнюю строку буфера — тот же принцип, что и вставка/удаление строк при ресайзе (см. выше), просто применённый к одной конкретной строке вместо целого блока картинки.

**`clear` останавливает воспроизведение всех плееров таба**: до этой правки реальный `clear` (шелл-команда) уже "прятал" виджет бесплатно (placeholder-ячейки — обычный текст, стираются реальным VTE как любой другой), НО плеер оставался живым и продолжал играть невидимо, без способа его остановить (виджет пропал, кликать больше не по чему). Пользователь подтвердил требование прямо: "команда clear должна останавливать и удалять все виджекты проигрывания из таба". Сложность — реальный `clear`, пришедший от шелла через настоящий PTY, обрабатывается ФОНОВЫМ потоком `alacritty_terminal::event_loop::EventLoop` целиком внутри форкнутого крейта, без единого события уровня "экран очищен" наружу (`AlacTermEvent` до этой правки не содержал ничего подобного — только `Wakeup` после ЛЮБОЙ мутации грида, что не различает "видимый контент реально стёрт" от "просто проскроллен за пределы viewport"). Пользователь явно указал: скролл трогать не нужно (плеер должен продолжать играть вне видимой области и виджет должен появляться обратно при скролле назад — то же самое поведение, что уже реализовано для картинок), нужно различать именно РЕАЛЬНЫЙ clear.

**Фикс — ещё один патч форка `errordnk/alacritty`** (ветка `som-disable-reflow`, коммит `fb1a87b6` → `8fa56a5b`): добавлен новый вариант `Event::ClearScreen`, эмитируемый из `Handler::clear_screen`, но ТОЛЬКО при `ansi::ClearMode::All` (реальный `CSI 2J`, ровно то, что шлёт настоящий `clear`/`Clear-Host`) — не при `Above`/`Below` (частичная очистка) и не при `Saved` (только scrollback, ничего видимого не стирает). Проверка через `matches!` (не `==` — `ClearMode` не реализует `PartialEq`, объявлен в стороннем крейте `vte`). `Cargo.toml`'s `alacritty_terminal` rev обновлён `fb1a87b6` → `8fa56a5b`. Som-сторона: `AlacTermEvent::ClearScreen` в `process_event` вызывает `Terminal::close_all_rich_content_audio_playback()` — закрывает КАЖДЫЙ открытый аудио-плеер безусловно (не пытается фильтровать по видимости на текущем кадре, что раньше по ошибке путало "не видно сейчас" со "стёрто навсегда" — первая отклонённая реализация закрывала любой плеер, чьи ячейки не видны в ТЕКУЩЕМ paint-кадре, что ломало бы обычный скролл; отменена до коммита после явного уточнения пользователя).

Тесты: `terminal` крейта rich_content-набор (69 тестов) и `test_clear_command_hides_placeholder_grid_cells` подтверждены зелёными после каждого из трёх изменений. Пред-существующие сбои в `terminal_hyperlinks` (28 тестов) не связаны с этой работой — воспроизводятся идентично на чистом дереве без каких-либо изменений этой сессии.
